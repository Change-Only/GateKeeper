### 2.1 应用凭证轮换：路径式 → 请求体式（**真缺口，已修**）

后端 `AppCredentialController`（`POST /rotate` L94–97 / `POST /complete-rotate` L106–110）**签名固定**为 `@RequestBody CredentialRotateRequest{appId, envCode}`（复合键 `appId+envCode`）。

| 能力 | 前端（原，错） | 后端（正确） | 处置 |

| 灰度轮换 | `POST /app-credential/${id}/rotate`（原 `modules.js:492`） | `POST /app-credential/rotate` + body `{appId, envCode}` | ✅ 已改（T07-B） |

### 2.2 授权域：双控制器并存（**R1 裁定 = 回退前端、保留双控；T07 选定 `/grant`**）

## 5. 偏差记录（两处前提更正 + 一处已修 + 一处真问题 + 一处类缺陷）

### 偏差 1（**已更正，经 team-lead 独立复核确认，不回退**）— 三域并非「半成品资产」，18/18 端点已实现
- **原判断**：三表与实体已有，但 Service / Mapper / Controller **文件数全为 0**，页面 404。
- **复核事实（以源码为准）**：三域**服务层齐全**（`alarm/`、`block/` 子包：entity + mapper + Service + ServiceImpl + Controller + ControllerTest）。端点 **18/18 已实现**（见 §1）。
- **真实缺口**：仅 **`DELETE /api/notify-channel/{id}`（N5）+ 3 个缺权限点（`alarm_rule:test`/`notify_channel:test`/`notify_channel:delete`）** —— **均 T07-A 已补齐**。
- **误判根因**：三域 Controller 在**子包**，被按 `controller/` 平铺目录 grep 漏掉 ⇒ **按目录检索的假阴性**（§7 案例③）。
- **决定**：**不重建三套服务层**。

### 偏差 2（**已更正 → R1 裁定为回退**）— 授权域并非 404，后端存在两个并行控制器
- **原判断**：后端无 `/grant` 前缀 ⇒ `PermMatrix.vue` 整页 404，判定「改前端换前缀」——**错误**。
- **复核事实**：`com.gatekeeper.grant.GrantController @/grant`（8 端点）**已在 HEAD 提交**；原前端 `/grant/*` 与其**逐字匹配** ⇒ **原本零 404**。另有并行控制器 `PermissionController @/permission`（10 端点）。两者**同包 `GrantService`**。
- **误判根因**：`GrantController` 在**子包 `grant/`**，按 `controller/` 目录扫描漏掉 ⇒ 与偏差 1 **同类的假阴性**（§7 案例③）。
- **裁定结果（R1）**：**前端回退 `/grant`、保留双控**（理由见 §2.2）。SE-5 那版 `/permission/*` 是**净回归**（丢 `envCode`/`status` 筛选），其自报的「实测 404」极可能是**后端未重启的 stale 假象**。已指派 SE-5 回退，并要求 eng-t03b 用真实 HTTP 给出 `/grant/list` vs `/permission/list` 的裁决性状态码。

### 偏差 3（**真缺口，已修**）— 凭证 `rotate`/`complete-rotate`：路径变量 → body 复合键
- **事实**：后端 `POST /app-credential/rotate` + `@RequestBody {appId, envCode}`；原前端写 `/app-credential/${id}/rotate` ⇒ **必 404**。
- **根因**：后端按**业务复合键**建模，前端按**单主键 id** 调用（列表 row 只有 id）。**T07-B 已修**。

## 7. 核查纪律（假阴性案例集）

> 本轮与 T06 连续出现**同型问题**：**结论「某能力不存在 / 某接口 404」多为核查手段所致，而非事实**。以下为已确认案例，**要求后续所有「缺失 / 404 / 未实现」判定**先自检。

| # | 假阴性案例 | 核查手段缺陷 | 正确做法 |
|---|---|---|---|
| ① | **权限码扫描器漏扫**：曾判「某批码未播种」 | 扫描器未处理 `core.quotepath` 中文转义、未覆盖 `router/` | `git -c core.quotepath=false ls-files`；范围含 `router/`、`api/`、`views/` |
| ② | **`grep -nA30` 截断方法体**：曾判 T06 `overview()` 缺 `securityEventCount` | 固定行窗口截取，函数体 >30 行被截断 | 按**函数名**全仓检索 + 读完整方法体 |
| ③ | **按目录计数漏子包**：判「三域服务层=0」（偏差 1）、「授权域 404 / 无 GrantController」（偏差 2） | 按 `controller/` **平铺目录**做文件计数，漏掉同职责子包（`alarm/`、`block/`、`grant/`） | 核查「能力是否存在」须**按类名 / `@RequestMapping` 全仓检索**（`grep -r '@RequestMapping("/grant")' src/`），**不能按目录范围判定** |
| ④ | **`git ls-files quotepath`**：曾漏判中文/特殊路径文件存在性 | 未加 `-c core.quotepath=false`，中文被转义无法比对 | 统一 `git -c core.quotepath=false ls-files`；或直接以 `Glob`/`Grep` 为准 |
| ⑤ | **孤儿文件误当在用**：`views/permission/Index.vue` 未被路由，却据此判 `/permission` 为准 | 未核 `router/index.js` 实际挂载 | 判「页面在用」必须核对路由挂载点；未挂载文件不计入调用面 |

> **🔴 第 4 次假阴性的实际代价（必须写实，否则纪律不会被遵守）**
> 按 `controller/` 目录 grep 得出「三域服务层为零」后，差点让实现方**重建三套完整服务层**（AlarmRule / BlockRule / NotifyChannel 的 Mapper + Service + ServiceImpl + Controller）。而这三套 Controller **本就存在于 `alarm/`、`block/` 子包** —— 重复建一份**相同 `@RequestMapping`** 的 Controller 会触发 Spring **`Ambiguous mapping`** ⇒ **整个后端起不来**（不是报错、不是功能降级）。这就是本节存在的理由。

**执行纪律（写进流程）**：任何「X 不存在 / Y 404 / Z 未实现」的结论，必须附**可复现的检索命令与命中结果**（`grep`/`Glob` 全仓），且命令**覆盖子包与子目录**；仅凭「某目录下没有文件」**不得**下否定结论。
**团队备忘建议（SE-5 提出，已并入本纪律）**：后端**全量 `@RequestMapping` 必须按包全量扫描**，不能只看顶层 `controller/` —— 可作为后续校验脚本的一条规则（脚本属新增产物，待 team-lead 决定是否产出）。

## 8. 验收判据

> **核心教训（呼应 T05）**：**只验接口返回 200，或只验页面能打开，都会漏掉本轮这类断头功能。** 必须验到「数据落库」。

1. **三域 CRUD 全链路**（`SysAlarm.vue` / `MonBlock.vue` / `SysNotify.vue`）：页面**可见 + 点得进去**；分别执行**新增 → 查询 → 修改 → 删除/停用**，每步**返回 200 且数据实际落库**（`SELECT` 对拍）；**`DELETE /api/notify-channel/{id}`（N5）必须实测**。
2. **测试端点**：A6 `/alarm-rule/{id}/test`、N6 `/notify-channel/{id}/test` 返回 200；**无 `*_:test` 权限角色须 403、有权限角色须 200**。
3. **授权域（**T07 选定 `/grant`**）**：`PermMatrix.vue` 列表可加载**且 `envCode`/`status` 筛选生效**；**新建 / 通过 / 驳回 / 撤销 / 延期**各返回 200 且 `app_api_grant` 数据变更；**撤销须走 `POST /grant/{id}/revoke` + body `{revokeReason}`（`@NotBlank`）**，不得用 `DELETE /permission?…`。
4. **凭证轮换**：`rotate` / `complete-rotate` 用 body `{appId, envCode}` 后返回 200 且 `app_credential.rotateFlag` 0/1 流转正确。
5. **权限点判据**：
   - `SELECT perm_code FROM sys_menu WHERE perm_code IN ('alarm_rule:test','notify_channel:test','notify_channel:delete')` 应存在（id 342/343/344）；
   - `SELECT r.role_code FROM sys_role_menu rm JOIN sys_role r ON r.id=rm.role_id WHERE rm.menu_id>=342 GROUP BY r.role_code` 应含 **`SUPER_ADMIN` + `ADMIN`**（342 另含 **`OPERATOR`/`BIZ_ADMIN`**）—— **按 §3.2 域镜像口径，不是通用三角色**；
   - `block_rule:test` **不应存在**（全局零引用，不播种）；
   - 落库后 `DEL gk:perm:*`；admin 重新登录验证 `permCount` 增加。
6. **按钮闸门对拍**：逐按钮核对「前端 `perm` 码」==「后端端点 `@RequirePerm` 码」（§6.2）。
7. **反面判据（防复发）**：不得出现「页面能打开、按钮能点，但提交后 404/403」；不得出现「只验 200 就判通过」。
8. **「端点存在 ≠ 端点能用」判据（以 §5 Class G 为反面教材）**：`GET /notify-channel/list` **端点存在、返回 HTTP 200、后端代码无异常**，但前端按 `data.records` / `data.total` 解析后端返回的**裸数组** ⇒ `records` 恒 `undefined → []` ⇒ **列表恒空且不报错**。故验收必须**逐端点对拍「后端返回形态」与「前端解析形态」**（裸数组 vs 分页信封），**不能只验「接口 200 / 页面能打开」** —— 那种验法对这类静默失效 100% 漏检。
9. **回归基线（team-lead 亲跑）**：`mvn -o test` = **`Tests run: 374, Failures: 0, Errors: 0, Skipped: 0` → BUILD SUCCESS**（T07 前基线 353，本轮净增 21 用例）。提交前须复跑到该数字。

### 8.1 验收方法（按缺陷类别）— 本轮最值钱的教训

> **本轮 T07 发现的三个缺陷，没有一个是「build 通过 + curl 200」能发现的**：
> ① 权限缺口（可直连 `curl` **绕过** UI 闸门）；② 裸 `el-button` **假闸门**（前端拦不住）；③ 信封解析 **静默恒空**。
> 三者都是**语义缺陷** —— 接口 200、页面能开、无异常日志，但**功能实际不可用 / 不安全**。

**纪律：语义类缺陷必须用「能失败的用例」验收，而不是「接口返回 200 即算过」。**

| 缺陷类别 | 特征 | **必须的验收方式** | 只看 200 会怎样 |
|---|---|---|---|
| **Class F · 权限/授权类** | 端点加了 `@RequirePerm` 但未播种；UI 有闸门但后端无注解（**假保护**）；或后端有注解但 UI 无闸门（**无权者可见、点了 403**） | **用低权角色反向验证：期望 403**。有权限角色 200、**无权限角色也必须 403**；并用**直连接口（curl）**验后端闸门独立成立，不能只靠 UI 隐藏按钮 | 管理员 `curl` 200 ⇒ 以为通过，实则**任何登录用户直连都 200**（闸门形同虚设） |
| **Class G · 静默空列表** | 前端解析形态 ≠ 后端返回形态（裸数组 vs `PageResult` 信封）⇒ `records` 恒 `undefined → []` | **断言列表非空**：用「已知有数据」的场景打开页面 / 接口，**断言 `list.length > 0`** 或页面行数 > 0 | 接口 200、页面能打开（空表）⇒ 绿灯，**缺陷 100% 漏检** |
| 一般 · 路径/形状错配 | 前端 path/method/params/body 与后端不符（如偏差 3） | 逐端点对拍 path + method + params + body + **返回形态**（§6） | 报错类可见，静默类不可见 |

- **通用规则**：验收用例必须**具备失败能力（fail-capable）** —— 若一个用例在缺陷存在时**照样通过**，它就不是验收，只是走过场。
- **对 T05「页面已完成」验收的追责性结论**：T05 三个 Phase 的验收口径是「build 通过 + 接口 200」，**对 Class G 是全盲**；后续验收须补「**低权角色 403**」与「**列表非空**」两类断言。
