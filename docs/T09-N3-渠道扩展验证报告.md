## 5. 偏差与裁定（4 条，全部留档）

### D1 🔴 掩码口径：方案 §3.3 与 §7.6 自相矛盾（已裁定并落地）
- **冲突**：§3.3 要求「password 替换为 `toSecretMask` 掩码（首4+****+末4）」，§7.6 要求「响应**不含明文与密文**」。实现者按 §3.3 把掩码套在**存储值**上，并把断言写进测试（`assertEquals("enc:****Zg==", ...)`）。
- **E2E 实测后果**（U4）：`enc:` 密文行返回 `enc:****Sbs=`（泄漏密文末 4 字符，无 KEK 不可利用）；但同一逻辑套到**历史明文行**（§3.3 读路径明确承认的合法存在态）会返回 `P@ss****1234` —— **泄漏真实密码首末各 4 位**。
- **裁定（lead，2026-09-13）**：**绝不泄漏明文片段优先**——
  - `enc:` 密文行 → 保留 §3.3 格式（首4+****+末4），泄漏的仅为密文片段且 `enc:` 前缀本身用于提示「已加密存储」；
  - 历史明文行 → 返回固定 `"****"`，**不派生自存储值**。
- **落地**：`NotifyChannelServiceImpl.maskForResponse` + 常量 `MASK_ONLY`；新增**能失败的用例** `list_legacyPlaintext_maskDerivesNothingFromPlaintext`（断言不含 `P@ss`/`1234`，旧实现下必红）。两种掩码均被 `isMaskedPassword` 识别 ⇒ 掩码回写防线（T6）不受影响；明文行经前端保存后仍会被正常加密迁移。
- **前端无形态依赖**（grep 确认），改动无跨端影响。

### D2 🟡 卫生 SQL 的前提在当前 dev 库**不成立**（已执行并留痕）
- `t09-notify-hygiene.sql` 旨在清理「`channel_config IS NULL` 却显示 `发送成功`」的失真行。实测 dev 库该组合 **0 行**（R3 描述的 4 行失真数据实际不存在）。
- **执行结果**：`affected rows = 0`；**幂等重跑仍为 0**。库中另有 1 行 `连接超时，请检查配置` 被正确**保留**（真实失败记录，非失真数据）。
- 结论：该 SQL 属**防御性、当前为 no-op**，保留在 `docs/sql/` 供其它环境使用，不阻塞交付。

### D3 🟢 接入 `WEBHOOK` 通用类型 + 修正注释漂移（超出 §2.1 原范围，已留档）
- **依据**：前端 `enum.js:226` 与 `SysNotify.vue:175` 均把 `WEBHOOK` 作为可选渠道类型并提供 `{webhook}` 配置入口。若后端维持桩发，**配置好的 WEBHOOK 渠道会「假成功」** —— 正是本项目反复铲除的缺陷类。故 `WebhookSender.supportTypes()` 含 `WEBHOOK`（响应无 `errcode` 结构时按 2xx 判成功，语义安全）。
- **连带修正**：`NotifySender` 的 Javadoc 与行内注释原写「SMS / WEBHOOK / 其他 → 桩发」，与实现不符，**本轮已订正**（仅注释，无行为变化）。

### D4 🟡 两处安全/健壮性 nit（**未修，留档**）
1. `EmailSmtpSender.cacheKey()` 以 `host|port|user|password` **原文**作键 —— 明文口令驻留内存 Map key。建议下一轮改为 `hash(password)`（或仅用 host:port:user 作键）。
2. 邮件主题/正文编码随 JVM 默认字符集（本机 Windows 为 GBK，实测报文 `Subject` 为 GBK-QP）。容器内通常为 UTF-8，建议显式设置 `DefaultEncoding`/`mail.mime.charset` 以消除跨环境差异。
3. 方案 **R8（KEK 轮换连带）** 仍为「仅留档、未实现」——`aes-key` 轮换需 `channel_config` 与 `app_secret` 同批重加密。

## 6. 方法纪律沉淀（可复用）

1. **规格内部矛盾必须在验证阶段暴露**：§3.3 与 §7.6 冲突只有在「历史明文行」这一非主路径上才显形 —— 只跑密文行主路径会得到「全绿」的假象。**验证要主动构造非主路径数据形态**（本次为「明文存量行」）。
2. **降级验证优于「接口 200」**：mock SMTP 收到真实报文、mock webhook 的 `errcode≠0` 让 `last_test_result` 落为 `FAILED` —— 这两条是本轮唯一能证明「真发/真判」的证据，单测 mock 无法替代。
3. **改脚手架（构造器）导致的既有测试改动必须逐条读**：本次 2 个文件仅 +CryptoService mock，**无断言弱化** —— 该检查应成为每次收口的标准动作。
4. **注释漂移与实现漂移同样要抓**（D3）：`NotifySender` 的 Javadoc 与 `supportTypes()` 不一致，正是 T08 教训（"闸门↔注解必须两端对齐"）的注释版。
