| --- | --- | --- |

## 1 平台级加解密总开关（需求一）

### 1.1 为什么挂在「安全策略」页而不是「加解密管理」

`/encryption` 页（`views/encryption/Index.vue`）**只有路由、没有菜单入口**
（路由 `{ path: 'encryption', name: 'EncryptionConfig', meta: { title: '加解密管理' } }`，
且**无 `meta.perm`**）⇒ 普通角色根本进不去。
本开关挂在**已有菜单 + 已播种权限**的 `/sys/sys-security`（安全策略页）新增 Tab 上，
并**默认选中该 Tab**（`activeTab: 'enc'`），避免"做了功能但没人找得到"。

### 1.2 表 `sys_encryption_config`（单行表）

| 列 | 说明 |
| --- | --- |
| `id` | 主键，**固定为 1**（`@TableId(type = IdType.INPUT)`，**非自增**） |
| `enabled` | `1`=启用（按各层级配置解析）/ `0`=**全局强制明文**，默认 `1` |
| `remark` | 变更备注（审计用，可空） |
| `updated_by` | 操作人 id |
| `created_at` / `updated_at` | 时间戳 |

**刻意不加的列**：`algorithm` / `key` / `iv` / `mode` / `padding` / `env_code` / `version`
—— 均为「不留平台密钥」口径的直接结果（见 §0）。

### 1.3 🔴 缺行 = 启用（零迁移的关键）

DDL **刻意不播种任何行**：

| 情形 | 行为 |
| --- | --- |
| 存量库（未跑脚本） | 表不存在 ⇒ 需先建表；建表后 0 行 ⇒ 视为**启用** |
| 新建库 / 跑过脚本 | 0 行 ⇒ 视为**启用** |
| 有人把行删了 | 0 行 ⇒ 视为**启用** |

三种情况行为完全一致 ⇒ **零迁移风险**（这也是"单行表 + 缺行=启用"而不是"必须有一行"的原因）。
`GET /sys/encryption-config` 在缺行时返回 `enabled=1` 的**虚拟行**（`id=1`，**不落库**），
前端因此不必为"从未配置过"写分支。

### 1.4 生效优先级（短路位置）

`EncryptionHandler.loadEncryptionConfig()` **最前面**：

```
【T16-1 平台总开关】enabled=0 ⇒ 直接 return（全局强制明文，忽略以下全部）
  ↓ 否则
接口级（api_interface 的 api_encryption_config，存在即终止）
  > 分组级（沿 parent_id 上溯；ENABLED 命中采用 / DISABLED 命中终止且不回退）
    > 应用级
      > 明文
```

网关责任链 Order（现行，未变）：
```
0 SysAccessWhitelistHandler -> 1 AppAuthHandler -> 2 IpWhitelistHandler
-> 3 IpBanCheckHandler -> 4 RateLimitHandler -> 5 PermissionHandler
-> 6 EncryptionHandler / VersionRouteHandler -> 7 AbnormalParamCheckHandler
-> 8 ForwardHandler -> 9 LogHandler
```
⇒ 总闸关闭时，请求**不再被 Order 6 拦**，会一路走到 Order 8 转发环节。

### 1.5 🔴 fail-safe 方向与访问白名单**相反**（最容易照抄错的一点）

| 组件 | 查询异常时的行为 | 理由 |
| --- | --- | --- |
| `SysAccessWhitelistHandler`（T15-4） | **fail-open 放行** | 它防的是"误拦"，基础设施抖动不应把全站打死 |
| `SysEncryptionConfigService.isGloballyEnabled()`（T16-1） | **保持加密（返回 `true`）** | 它是「把全平台降级为明文」的**闸门**；一次 DB 抖动绝不能松闸 |

> ⇒ 新增类似"闸门型"开关时，**方向必须按闸门语义定，不能照抄上一个 fail-open**。

### 1.6 缓存契约

- `volatile Boolean cachedEnabled` + `volatile long cachedAt`，`CACHE_TTL_MS = 10_000L`
  —— 省网关热路径每次一次 DB 往返。
- **写后立即 `invalidate()`** ⇒ 用户点保存即刻生效（不必等 TTL）。
- **异常路径不写缓存** ⇒ 避免"默认值被缓存住导致开关永远读不出来"。
- 多实例部署：写实例立即生效，其余实例**最长 10 秒收敛**（前端已明示）。

### 1.7 端点与权限

| 端点 | 权限点 | risk | 备注 |
| --- | --- | --- | --- |
| `GET /sys/encryption-config` | （只读，**不加注解**） | — | 缺行返回 `enabled=1` 虚拟行 |
| `PUT /sys/encryption-config` | `sys:security:update`（**复用既有码**） | 1 | body 至少含 `enabled`(1/0)，可选 `remark` |

- **不新增权限点**，直接复用既有、已播种、已授权的 `sys:security:update`
  —— 避开「新增码忘授权 ⇒ 连 SUPER_ADMIN 都拿不到」（本项目历史坑，见 §16.2）。
- 只读 `GET` 沿用仓库约定**不加 `@RequirePerm`**（`AppController` 全部 list/GET 均无注解）。
- 非法值（`null` / `2` / `-1` / 缺 `enabled`）一律 **400**，**不做隐式默认纠正**。
- 更新走 `UpdateWrapper` 显式 `set`（`updateById` 的 NOT_NULL 策略写不进 `null`，
  否则 `remark` 清空会静默失效 —— 同 T15-4 白名单的教训）。

## 2 应用接口文档导出（需求二）

### 2.1 🔴 「有权限」的判定（与网关口径对齐，别自行放宽）

三个条件**全部满足**才导出：

1. `app_api_grant.status = 1`（**已生效**）
   —— 待审批(0) / 已过期(2) / 已撤销(3) / 已驳回(4) **一律不导出**
   （网关 `PermissionHandler` 对这几态也是直接拒，导出了就是骗调用方）；
2. 在有效期内：`valid_from <= today <= valid_to`，两者均可为 `NULL`（NULL = 不限制）；
3. 接口存在且 `api_interface.status = 1`（网关启用）。

### 2.2 被剔除的两类**分别计数**（让数字可解释）

| 字段 | 含义 |
| --- | --- |
| `danglingCount` | 授权指向的接口**已删除**（或 `api_id` 为 `null`） |
| `disabledCount` | 接口存在但**已停用**（`status != 1`） |

⇒ 「导出条数 < 授权条数」时可以直接解释：**导出 N + 悬空 A + 停用 B = 生效授权数**，
而不是让人对着数字猜。前端在导出成功提示里也会带上这两项。

### 2.3 查询策略（四步批量，无 JOIN / 无 N+1）

授权（`QueryWrapper` 内下推全部过滤，含 `valid_from`/`valid_to` 的 NULL 兼容）
→ 接口（**含停用的**，才能区分"悬空"与"停用"）→ 分组名 → `api_param`，
每步单条 `IN` 批量 SQL。

- 本仓 mapper 层**无 XML**（全 Wrapper），且 `api_param` 是 1:N 子表
  ⇒ `JOIN` 会把结果揉成笛卡尔积还要在 Java 侧去重，故在内存拼装。
- **同接口多环境授权 = 多行**（环境是授权维度）。
- 稳定排序：清单按「分组名 → 接口路径」；参数按 `paramType` → `sortOrder` → `id`
  （三者 NULL 统一 `nullsLast` 兜住）。
- 分组/接口被删**不报错**（分组名留 `null`，`params` 保证非 `null`），避免整体导出失败。

### 2.4 端点与权限

| 端点 | 权限点 | 备注 |
| --- | --- | --- |
| `GET /app/{id}/interface-doc` | （只读，**不加注解**） | 应用不存在 ⇒ **400**（不是 500 / 不是空清单） |

- 只返回**数据**（`AppInterfaceDocVo`）；**Markdown 正文由前端 `utils/interfaceDoc.js` 生成**
  —— 与 T14 接入文档同一取舍：**正文口径只在一处定义**，
  否则后端再做一套模板，两边迟早发散（最典型的是"文档里的签名算法与页面讲的不一致"）。
- 前端复用 `@/utils/accessDoc` 的 `downloadTextFile` / `safeFileName` / `formatNow` / `GK_HEADERS`。
  🔴 `downloadTextFile` 内部已补 `;charset=utf-8` ⇒ 传 MIME 时**只传基础类型**
  （`'text/markdown'`），否则会拼成 `text/markdown;charset=utf-8;charset=utf-8`。
- 入口两处：应用列表**行操作「接口文档」** + 详情抽屉**头部按钮**（对 `currentApp` 生效）。

### 2.5 文档结构（Markdown）

标题 + 元信息（应用名 / AppKey / 授权接口数 / 网关入口 / 生成时间）
→ 「仅包含该应用已被授权且当前生效的接口」说明 + 可解释的剔除计数警示
→ 一、调用约定（认证头表 + 签名口径）→ 二、接口清单总表
→ 三、接口明细（元信息表 + 按 `paramType` 分节的参数表）。
空清单时给「请先在接口授权总览申请授权」的引导文案。

**E2E 断言可证伪性（关键设计，不是"改后看起来对"）**：

- A 组（总开关）：先给接口配 SM4 + 16 字节密钥 + `requestEncrypted=1`，构建**可证伪三段论**：
  1. **基线**：总开关缺行（=启用）+ 走网关发明文 ⇒ 命中 `400 入参解密失败`
     —— 先证明"接口级配置确实在网关进程里生效"，否则后面"没报解密失败"可能只是因为压根没配置；
  2. **关闭**：`enabled=0` ⇒ **同一请求**报文变成 `502 后端服务连接失败`（`backendUrl` 固定指向
     `127.0.0.1:9`，必然拒连 ⇒ 文案确定性），即**已推进到 Order 8 转发环节**，
     证明 Order 6 被整段跳过；同时后端日志新增「平台加解密总开关已关闭」
     —— 这句只可能由新加的短路分支打印（smoking gun）；
  3. **恢复**：`enabled=1` ⇒ 同一请求**重新**报 `入参解密失败`（双向可逆，
     排除第 2 步是缓存残留/偶发）；
  4. 非法值 `5/-1/2/缺 enabled` ⇒ 400 且库里仍是被写下的那个值（拒写而非静默纠正）；
  5. 删行 ⇒ `GET` 仍报启用、网关仍按加密处理（"缺行≠明文"）。
- B 组（接口文档）：灌 7 条姿态各异的授权 ——
  `status=1` 且有效期内（导出）、`status=0` 待审批、`status=3` 已撤销、
  `valid_from` 在未来（未生效）、`valid_to` 在过去（已过期）、
  `api_id` 指向不存在接口（悬空）、指向已停用接口（停用）
  ⇒ 断言 `total=1`、`danglingCount=1`、`disabledCount=1` 且
  **1+1+1=3** 计数自洽；再验同接口双环境 ⇒ `total=2`（环境是授权维度）、
  参数按 `paramType` 升序、应用不存在 ⇒ 400、无授权应用 ⇒ 空清单。

## 4 本轮的环境级坑（工程经验，非契约）

### 4.1 🔴 后端日志是 **GBK**，不是 UTF-8

`restart_backend.py` 用 `subprocess.Popen(stdout=logf)` 把子进程 stdout 直接重定向到文件，
子进程（Java）按系统默认代码页（中文 Windows = cp936/GBK）写字节，**绕过** Python 侧的
`encoding="utf-8"`。用 utf-8 读会得到 `��˷�������ʧ��` 这类乱码 ⇒
表现为「日志里明明有这句，断言却失败」。
**绕法**：以二进制读入，先试 `utf-8`，`UnicodeDecodeError` 再回退 `gbk`。

### 4.2 🔴 `app_api_grant` 有唯一键 `uk_grant_app_api_env (app_id, api_id, env_code)`

同 (应用, 接口, 环境) **只能有一行**。探针若想让"待审批"与"已生效"共存于同环境，
会撞 `1062 Duplicate entry`。**绕法**：每条干扰授权用**各自独立的 `env_code`**；
这样反而让断言更干净 —— 干扰行在"接口存在且启用、无有效期限制"上与生效行完全等价，
唯一差别就是 `status`/接口状态/有效期 ⇒ 它们不出现就只能是被对应条件筛掉的。

### 4.3 🔴 同文档 hash 导航 + 通用选择器 = 假通过

`/#/sys/sys-security` → `/#/app` 是**同文档 hash 导航**：`location.hash` 同步生效，
但 Vue 换组件是异步的。若 `waitFor` 只等通用选择器（如 `.crud-table tbody tr`），
会被**上一页残留的 DOM**（安全策略页也有 CrudTable 规则表）立刻满足 ⇒
拿到旧表格的行去找目标值 ⇒ 恒为 -1。
**绕法**：等**目标页独有**的锚点（如 AppList 工具栏的「系统访问白名单」按钮 + 探针应用名出现在 `body.innerText`）。

### 4.4 🔴 `waitFor` 的完成条件不要包含"存在 el-message"

Element UI 的 `el-message` 生命周期 3s，**跨路由切换仍留在 DOM 里**。
把 `messages().length > 0` 当作"动作完成"会让 `waitFor` 秒回 ⇒
在 axios 返回前就读结果 ⇒ 整段误判为"没触发下载"。
**绕法**：完成条件只盯**本次动作的产物**（如 `!!window.__dlBlob`），并在点击前清掉遗留 toast。

### 4.5 `pymysql` 连接必须 `try/finally` 关闭

探针里若某条 SQL 中途抛异常而漏关连接，会留下一个未提交事务把表锁住，
后续 `DELETE` 直接 `1205 Lock wait timeout exceeded`（首次跑探针就是这么被绊的）。

## 5 已知限制 / 未做

- 总开关**没有操作审计流水**（仅 `updated_by` / `updated_at` 落在单行表上）；
  若后续要求"开关变更历史"，需另起审计表（当前 `@RequirePerm(risk=true)` 已进入鉴权链）。
- 总开关**不分环境**（刻意：它是平台级总闸）。
- 接口文档**不导出响应示例 / Mock 报文**（只导出定义：元信息 + 参数 + 调用约定）。
- 多实例部署下开关最长 10s 收敛（见 §1.6）。
