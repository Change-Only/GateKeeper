## 1 保护对象：加密什么、刻意不加密什么

### 1.1 掩码范围（**刻意的取舍，不是漏做**）

**加密 / 掩码**（契约内容，泄漏即等于泄漏接口定义）：
- `api_interface.interface_path` —— 接口路径
- `api_param.field_name` —— 字段名
- `api_param.example` —— 示例值
- `api_param.description` —— 字段说明

**刻意不加密**（否则功能不可用）：
- `api_interface.backend_url` —— 上游地址，**非**对外契约；加密后运维无法排障
- 接口 / 分组 / 应用的**名称类**业务信息 —— 加密后列表页只剩密文，无法导航
- `api_param` 的**结构列**：`param_type` / `field_type` / `required` / `error_code` /
  `http_status` / `sensitive` / `encrypt_rule` / `sort_order`

🔴 **结构列不掩码是硬约束**：参数页要靠「类型 / 是否必填 / 参数类型」渲染表格骨架，
一旦连结构列也掩码，普通用户打开参数页就是**全空白**（连"这一行是个 int 必填项"都看不出）。
E2E `B8` 断言专门守住这点（掩码态下 `fieldType` / `paramType` 仍可见）。

### 1.2 密文格式与算法

- 算法：**AES-256-CBC + PKCS5Padding**，**每次加密生成随机 16 字节 IV**。
- 格式：`enc:v1:<base64(IV)>:<base64(cipher)>`（共 4 段，`:` 分隔）。
- 密钥：复用落库 KEK `gatekeeper.crypto.aes-key`（经环境变量 `GATEKEEPER_AES_KEY` 注入，
  **密钥值不在此文档登记**，见 `.env.example` / `application.example.yml` 的占位说明），
  经 `CryptoKeyUtil.toBase64Key` 规范化为 32 字节。
- **零迁移兼容**：读取时**无 `enc:v1:` 前缀一律原样返回** ⇒ 存量明文行无需任何迁移脚本。
- 加密失败 **FAIL-CLOSED**（抛异常拒绝落库）；**解密失败不抛**（原样返回 + WARN），
  否则一条坏数据会让整个列表页 500。
- `encryptField` **幂等**：已是密文则原样返回（防更新场景二次加密）。

### 1.3 🔴 盲索引：随机 IV 密文的代价与解法

**问题**：网关路由依据是 `interface_path`（`PermissionHandler` 原本
`eq("interface_path", candidate)` 直接查库）。随机 IV ⇒ **同一路径每次密文都不同**，
等值匹配永远不中 ⇒ **网关全量 404**。这是本任务最大的隐藏地雷。

**解法**：新增确定性列

```
interface_path_hash CHAR(64)
  = lower(hex( HMAC-SHA256( KEK, "gk:bidx:interface_path:" + 明文路径 ) ))
```

- 固定密钥、无盐、**带域分离前缀** `gk:bidx:interface_path:`（防与其他 HMAC 用途串用）。
- 用 **HMAC 而非裸 SHA256**：接口路径是**低熵**字符串（`/api/v1/order/{id}` 这类
  在字典里），裸摘要可被彩虹表秒破；带密钥的 HMAC 则必须持有 KEK 才能枚举。

**查询改造**（双分支 OR，兼容存量）：

```java
.and(w -> w.eq("interface_path_hash", h).or().eq("interface_path", candidate))
```

⇒ 密文行（hash 命中）、历史明文行（明文命中）**共存**，零迁移。

### 1.4 🔴 hash 与开关**解耦**

`applyToInterface()` **无论开关是否启用都写 hash**。

原因：若「关开关期间新建的接口」不写 hash，则「关过再开」之后这些行的
`interface_path_hash` 为 NULL、路径又是明文（能明文命中）——
**今天能跑，明天有人给它们补加密就全 404**。把 hash 视为**与开关无关的恒常产物**，
才不会有这种"埋雷"。E2E `C2` 断言专门覆盖：关开关期新建 ⇒ 落库明文**但 hash 仍在**。

### 1.5 开关表 `sys_interface_crypto_config`

- **单行表** `id` 恒 1，`IdType.INPUT`（非自增）。
- 🔴 **缺行 = 启用**：SQL **刻意不播种任何行** ⇒ 存量库 / 新建库 / 忘跑脚本行为一致 = **零迁移**。
  `GET` 缺行返回 `enabled=1` 的**虚拟行且不落库**。
- 缓存 `CACHE_TTL_MS = 10_000L`（多实例最长 10s 收敛）；**写后 `invalidate()` 立即生效**。
- 非法值（含缺 `enabled`）一律 **400 且不写库**；更新用 `UpdateWrapper` 显式 `set`。
- 删除行即回到「缺行 = 启用」。

### 1.6 🔴 fail-safe 方向通则（本轮固化）

> **准入闸门**异常 ⇒ **fail-open 放行**；**保护闸门**异常 ⇒ **fail-safe 收紧**。

- `sys_ip_whitelist` / `SysAccessWhitelistHandler`：异常 = 拿不到黑名单 ⇒ **放行**（别把人挡在门外）。
- 本任务的开关与可见性判定：异常 = 拿不到"是否该解密/该可见" ⇒ **保持加密 / 掩码**
  （宁可让人看不到，也不能让不该看的人看到）。
- T16-1 总开关同理（异常 ⇒ 保持加密）。

**新闸门先问语义：它是"放行凭证"还是"保护屏障"，再定方向 —— 别照抄上一个。**

## 2 控制台可见性白名单

### 2.1 判定顺序（`InterfaceViewer.canSee(ownerId)`）

```
① 开关关闭                    ⇒ 全可见（等效无保护）
② 是 SUPER_ADMIN              ⇒ 可见（兜底，防白名单把自己也锁死）
③ 是该接口 owner_id 本人       ⇒ 可见
④ 白名单为空                  ⇒ 不可见（只认 ②③）
⑤ 命中 (USER, uid) 或 (ROLE, 任一角色) ⇒ 可见
否则                          ⇒ 掩码 ****
```

### 2.2 🔴 空表方向与「系统访问白名单」**相反**（最容易混淆的一点）

| 表 | 语义 | 空表含义 |
|----|------|----------|
| `sys_ip_whitelist`（准入） | 允许谁**进来** | 空 = **不限制**（全员放行） |
| `sys_interface_visibility`（可见性） | 允许谁**看见明文** | 空 = **谁都看不见**（除超管/owner） |

两者名字都叫"白名单"，方向恰好相反。需求原话是"别人看不到我的接口信息"，
所以可见性表的空表**必须收紧**。E2E `B1` 断言：「空白名单 + 非 owner ⇒ 路径为 `****`」，
配套 `B8` 断言「结构列仍可见」，共同证明收紧只作用在内容列。

- 白名单支持两类主体：`subject_type ∈ {USER, ROLE}`，`status=1` 才参与判定
  （`B3` 断言：停用条目**完全不参与判定** ⇒ 回到掩码）。
- **孤儿行不自动清理**（主体被删后行仍留），VO 带 `subjectMissing/subjectCode` 让前端标红提示。

### 2.3 端点与权限（**零新增权限点**）

`InterfaceProtectionController`（`@RequestMapping("/sys/interface-protection")`）：

| 端点 | 权限注解 |
|------|----------|
| `GET /config` | 不加（仓库只读约定） |
| `PUT /config` | `@RequirePerm("sys:security:update", risk=true)` |
| `GET /whitelist` | 不加 |
| `POST /whitelist` | `@RequirePerm("sys:security:update", risk=true)` |
| `PUT /whitelist/{id}` | 同上 |
| `DELETE /whitelist/{id}` | 同上 |
| `GET /subject-options` | 不加 |

「零新增权限点」**不等于**「无保护」：E2E `B0b` 用普通用户打 4 个写端点
**全部 403**，同时用超管打同一端点（非法值 5）得 **400** —— 差分排除"路由不存在导致的假 403"。
普通用户 `GET /config` 仍 **200**（只读不受影响）。

## 3 🔴 掩码回写防线（不可逆数据损毁的唯一屏障）

**场景**：非授权用户看到的是 `****`，前端把 `****` 当值填回表单，用户"什么都不改点确定"
⇒ `****` 覆盖真值 ⇒ **原密文丢失、hash 丢失 ⇒ 该接口在网关永久 404，且不可恢复**。

这与 §8「表单往返静默改写」是**同一族缺陷**，故按同族标准审计了三处写入路径：

| # | 防线 | 位置 | 行为 |
|---|------|------|------|
| ① | 路径回填 | `InterfaceServiceImpl.applyPathWriteBackGuard` | 提交值为掩码/空 ⇒ 用库中**原密文与原 hash 回填**（该列 no-op） |
| ② | 参数跳过 | `ApiParamServiceImpl.update` | 三列中任为掩码 ⇒ **跳过赋值**（其余列照常更新） |
| ③ | 批量拒绝 | `ApiParamServiceImpl.assertNoMaskInBatch` | `batch-save` 是**先删后插**语义，原值已随"先删"消失 ⇒ 只能 **400**，且**先删不执行** |

E2E 证据：
- `D1` 掩码路径 ⇒ 200，且 **路径与 hash 完全未变**，读回仍是原明文。
- `D2` 掩码参数三列 ⇒ 200，三列**完全未变**，但 `fieldType/sortOrder` 的**正常修改照旧生效**
  （防线只保护内容列，不是把整行变只读）。
- `D3` batch-save 含掩码 ⇒ **400**，且**行数不变**（先删未执行）。

## 6 已知限制 / 未做

1. 🔴 **密钥轮换（R8）未实现**：KEK 与 `app_secret` 共用，轮换需**同批重加密**
   `app_secret` + 接口路径 + 参数三列 + `interface_path_hash`，本任务未做。
2. **`backend_url` 不加密**是设计选择（见 §1.1），若后续要求加密，需评估运维排障成本。
3. **掩码态下 batch-save 直接 400**：非授权用户无法用批量接口保存参数，
   体验上需要其逐行编辑（内容列留空/掩码即跳过）。这是**有意的**（宁可拒绝，不可损毁）。
4. **白名单仅支持 USER / ROLE** 两类主体，无「部门 / 应用」维度。
5. **孤儿白名单行不自动清理**，仅前端标记提示。
6. 盲索引使 `interface_path_hash` **可被持有 KEK 者枚举验证**（这是等值查询的必然代价）；
   若未来要抗该风险，需换可搜索加密方案（成本高，当前不必要）。

## 7 本轮新增的工程经验（非契约）

- 🔴 **`Write`/`Edit` 会「报成功但不落盘」** ⇒ 所有写文件后必须读回复核（本轮再次命中）。
- 🔴 **`git bundle create` 的路径必须是 Windows 风格**（`D:/...`）；Git Bash 的
  `/d/...` 风格会被 git 拒绝（`Unable to create '...lock': No such file or directory`）。
- 🔴 **探针 payload 必须字段齐全**：`PUT /api-param/{id}/update` 的 DTO 校验链要求 `apiId`，
  漏了会得 400「接口ID不能为空」，看起来像"防线没生效"，实为探针自身缺陷。
- **`PageResult` 在 `com.gatekeeper.common`**（不是 `com.gatekeeper.dto`）。
- **Mockito `deleteById(any())` 重载歧义** ⇒ 用 `anyLong()`。
- 🔴 **差分对照是"防平凡通过"的唯一手段**：`E3`（停用 ⇒ 404）、`B0b`（超管 ⇒ 400）
  都是为了让相邻的"不报 404 / 报 403"断言**有说服力**。没有对照组，绿灯不可信。
- 🔴 **UI 探针里"异步表格"必须等行数 ≥ 1 再读**：详情抽屉打开后参数表格是**异步**拉的，
  只等 `.hero-path` 出现就去读，会把"还没加载完"误判成"参数页对普通用户空白"
  （本轮一次假失败 4 条）。⇒ `waitFor(pane 内 tbody tr >= 1)`。
- 🔴 **断言产品文案必须逐字回到源码核对**：本轮两条 FAIL 纯属探针措辞 ——
  产品 Tab 是「接口**信息**保护」（不是「接口保护」）、掩码标签是「路径对当前账号**隐藏**」
  （不是「无权查看」）。凭印象写断言会把"文案不一致"误判成产品缺陷。
- **UI 探针（同一页面跑两个身份）是"掩码/可见性"类改动的最强证据**：单独看普通用户的
  `****` 无法排除"页面压根没渲染"，必须用有权限身份打**同一行**做对照。
