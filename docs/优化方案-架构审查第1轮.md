## 第二部分：高优先级问题修复方案（代码级）

### R1 密钥治理：默认值告警 + 启动自检（折中方案，不破坏本地启动）

**原理**：直接删默认值会让本地开发启动失败（配置解析报错），故采用"保留默认 + 启动强检测 + 生产 profile 强制为空"双保险。

修改 `src/backend/src/main/java/com/gatekeeper/config/SecurityConfigCheck.java`（新增）：

```java
package com.gatekeeper.config;

import lombok.extern.slf4j.Slf4j;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.boot.ApplicationRunner;
import org.springframework.stereotype.Component;

/**
 * 启动安全自检：检测是否仍在使用代码库中公开的默认密钥。
 * 生产环境使用默认密钥 = 任何人可伪造 JWT 管理员令牌 / 解密 AppSecret。
 */
@Slf4j
@Component
public class SecurityConfigCheck implements ApplicationRunner {

    private static final String DEFAULT_JWT  = "GateKeeperJwtSecret2026@Secure#Key";
    private static final String DEFAULT_AES  = "GateKeeper2026SecretKeyABCDEFGHI";

    @Value("${gatekeeper.jwt.secret}")
    private String jwtSecret;
    @Value("${gatekeeper.crypto.aes-key}")
    private String aesKey;

    @Override
    public void run(org.springframework.application.ApplicationArguments args) {
        if (DEFAULT_JWT.equals(jwtSecret)) {
            log.error("【安全告警】JWT 密钥使用默认值（已公开于代码库）！生产环境必须设置 GATEKEEPER_JWT_SECRET 环境变量，否则任何人可伪造管理员令牌。");
        }
        if (DEFAULT_AES.equals(aesKey)) {
            log.error("【安全告警】AES 数据库加密密钥使用默认值！生产环境必须设置 GATEKEEPER_AES_KEY，否则库中 AppSecret 等同明文。");
        }
    }
}
```

配套修改 `application.yml`（注释强化 + 上线清单）：

```yaml
# 修改前
  jwt:
    secret: ${GATEKEEPER_JWT_SECRET:GateKeeperJwtSecret2026@Secure#Key}
# 修改后（默认值保留仅供本地演示，启动时 SecurityConfigCheck 会打 ERROR 告警）
  jwt:
    secret: ${GATEKEEPER_JWT_SECRET:}   # 生产必填；为空时本地回退见 bootstrap 校验
```

> 需要你确认的取舍：方案 A（上述，温和）保留默认值+告警；方案 B（激进）默认值置空+启动失败。我推荐 A→待真实联调后再切 B。见第四部分 Q2。

### R2 自定义有界 @Async 线程池（新增 AsyncConfig）

**原理**：默认 ThreadPoolTaskExecutor 队列容量 `Integer.MAX_VALUE` ≈ 无界。改为**有界队列 + CallerRunsPolicy**：队列满时让调用线程（网关工作线程）自己执行日志写入，宁可该请求慢 5ms，也不让 JVM 被 OOM 杀死——背压（backpressure）思想。

新增 `config/AsyncConfig.java`：

```java
package com.gatekeeper.config;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.scheduling.concurrent.ThreadPoolTaskExecutor;

import java.util.concurrent.Executor;
import java.util.concurrent.ThreadPoolExecutor;

/**
 * @Async 统一线程池：有界队列 + CallerRuns 背压。
 * 默认池队列无界，网关高峰期日志/检测任务堆积会 OOM；
 * 本配置队列满时由调用线程执行，形成天然限流。
 */
@Configuration
public class AsyncConfig {

    @Bean("gatewayExecutor")
    public Executor gatewayExecutor() {
        ThreadPoolTaskExecutor ex = new ThreadPoolTaskExecutor();
        ex.setCorePoolSize(8);                 // 常驻线程：与日志写入（单条 insert）吞吐匹配
        ex.setMaxPoolSize(16);                 // 峰值扩容上限
        ex.setQueueCapacity(2000);             // 有界队列：约等于 2000 条排队日志
        ex.setKeepAliveSeconds(60);
        ex.setThreadNamePrefix("gk-async-");
        // 关键：队列满时调用线程自己跑（背压），而不是无界堆积或抛异常
        ex.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        ex.initialize();
        return ex;
    }
}
```

同时给所有 @Async 方法指定池名，避免 Spring 找不到唯一 Bean 的歧义：

```java
// 修改前
@Async
public void recordLog(GatewayContext ctx) { ... }

// 修改后
@Async("gatewayExecutor")
public void recordLog(GatewayContext ctx) { ... }
```

### R3 CSV 导出改分批游标流式写出

**原理**：流式处理（streaming）——每批只持 5000 条实体，写完即释放，内存占用从 O(总行数) 降到 O(批大小)；用 MyBatis-Plus 分页循环（以 id 游标推进），不用 offset 深翻页（OFFSET 越大 MySQL 扫描越多）。

`CallLogController.exportCsv` 核心改动：

```java
// 修改前：一次拉全量
PageResult<ApiCallLog> pr = callLogService.pageQuery(1, 100000, ...);
List<ApiCallLog> records = pr.getRecords();

// 修改后：按 id 游标分批拉取，边拉边写
private static final int BATCH = 5000;

Long lastId = 0L;
long total = callLogService.count(query);   // 先回 Count 供前端展示进度
try (PrintWriter writer = new PrintWriter(new BufferedWriter(
        new OutputStreamWriter(out, StandardCharsets.UTF_8), 64 * 1024))) {
    writer.println("日志ID,应用名称,接口路径,...");
    while (true) {
        // WHERE ... AND id > #{lastId} ORDER BY id ASC LIMIT 5000
        List<ApiCallLog> batch = callLogService.listBatchAfterId(lastId, BATCH, cond...);
        if (batch.isEmpty()) break;
        for (ApiCallLog row : batch) {
            writer.println(toCsvLine(row));
        }
        lastId = batch.get(batch.size() - 1).getId();
        if (batch.size() < BATCH) break;
    }
}
```

> 需在 `CallLogService` 增加 `listBatchAfterId(Long afterId, int limit, ...)`（QueryWrapper `gt("id", afterId).orderByAsc("id").last("limit " + limit)`），无第三方依赖。

### R4 SQL 日志改 Slf4j 且生产关闭

```yaml
# 修改前
  configuration:
    log-impl: org.apache.ibatis.logging.stdout.StdOutImpl
# 修改后
  configuration:
    log-impl: org.apache.ibatis.logging.slf4j.Slf4jImpl   # 走 logback，可按级别控制
```

`application.yml` 追加（控制 mapper 包 SQL 日志级别，生产默认 INFO 不打印 SQL）：

```yaml
logging:
  level:
    com.gatekeeper.mapper: warn        # 生产：warn；联调需要看 SQL 时改 debug
```

**原理**：StdOutImpl 绕过日志框架直接 `System.out.println`，同步阻塞且不可关闭；Slf4jImpl 纳入 logback 管线，异步可配、级别可控。**不改的后果**：QPS 稍高 stdout 即成瓶颈，且日志无法按环境关闭。

### R5 前端统一加载态与防重

以 `views/app/Index.vue` 为例（所有列表页同模式应用）：

```html
<!-- 修改前 -->
<el-table :data="list" border>
<!-- 修改后 -->
<el-table :data="list" v-loading="loading" border>
  <template slot="empty">
    <el-empty description="暂无应用，点击右上角「创建应用」开始"></el-empty>
  </template>
</el-table>
```

```javascript
// 修改前（无防护，连点 = 重复删除）
async remove(row) {
  await this.$confirm(...)
  await deleteApp(row.id)
  this.loadData()
},
// 修改后
async remove(row) {
  await this.$confirm(...)
  this.deleting = true
  try {
    await deleteApp(row.id)
    this.$message.success('删除成功')
    this.loadData()
  } finally {
    this.deleting = false            // 失败也复位，允许重试
  }
},
```

对应删除按钮 `:loading="deleting"`。**原理**：loading 是双向承诺——给用户"系统收到指令了"的反馈（PM 视角），同时锁住入口防重复提交（工程视角）。**不改的后果**：重复删除对幂等接口是浪费请求，对非幂等接口（创建应用）会产生脏数据。

## 第四部分：需要你确认的问题

1. **部署形态**：最终是单机 `java -jar`、Docker 容器、还是 K8s？——决定 R1 密钥注入方式（环境变量 / K8s Secret / 挂载 application-prod.yml）。
2. **密钥策略取舍**：R1 用温和方案（默认值保留 + 启动 ERROR 告警，本地开发不受影响）还是激进方案（默认置空、漏配即拒绝启动）？我推荐演示期 A、上线前切 B。
3. **日志导出量级预期**：单次导出预期最大多少行（1 万 / 10 万 / 百万级）？百万级建议第 2 轮直接做"异步生成文件 + 下载中心"而非同步流式。
4. **移动端适配优先级**：管理后台是否需要手机可用（运维半夜手机解封 IP 是真实场景），还是只保 1366×768 以上？影响第 7 轮工作量估计。
5. **SecurityDetectionService 重构时机**（第 5 轮）：策略模式拆分会动 5 个检测的调用方，你想现在重构，还是等真实环境联调完成、行为基线稳定后再动？——我建议**后者**：先有联调证据再重构，避免重构掩盖新问题。
