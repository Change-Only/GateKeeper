# T12 · 通知渠道新增「HTTP 自定义接口」· 契约记录

> **需求原文**：「通知渠道中增加接口告警，可以调用外部接口」
> **交付**：在既有通知渠道体系（T09）中新增第 5 种渠道类型 **`HTTP`（界面名「自定义接口」）**，
> 告警触发/渠道测试时按渠道配置向**任意外部 HTTP 接口**投递告警报文。
> **红线遵守**：**零新表、零新列、零新端点、零新权限码、零 DDL**；18 表结构不变；`migrate-v2.sql` 不动。

---

## 1 为什么要新增而不是复用 WEBHOOK

T09 的 `WebhookSender` 覆盖 `WECOM / DINGTALK / WEBHOOK` 三种类型，但它把报文**写死**为企微文本格式：

```json
{ "msgtype": "text", "text": { "content": "标题\n正文" } }
```

只对企微/钉钉系接收端成立。第三方运维平台/工单系统/自建回调通常要求：

| 需求 | WEBHOOK | HTTP（本次新增） |
|---|---|---|
| 自定义报文结构 | ✗ 固定 `msgtype/text` | ✓ `bodyTemplate` 模板 |
| 请求方法 | ✗ 固定 POST | ✓ POST / PUT / GET |
| 鉴权头 | ✗ 只能塞进 URL | ✓ `headers` + `${password}` |
| 内容协商 | ✗ 固定 JSON | ✓ JSON / 表单 / 纯文本 |
| 成功判定 | 固定读 `errcode` | ✓ 可配 `successJsonPath/Value`，留空则看 HTTP 状态 |
| 超时 | ✗ 无（JDK 默认无超时，黑洞即挂） | ✓ 默认 5s，可按渠道配置 |

## 2 渠道类型

| 项 | 值 |
|---|---|
| `channel_type` | **`HTTP`**（新增；追加到 `WECOM/DINGTALK/EMAIL/SMS/WEBHOOK` 之后） |
| 界面名（`enum.js`） | **自定义接口** |
| 后端适配器 | `com.gatekeeper.alarm.sender.HttpApiSender`（`@Component implements ChannelSender`） |
| 标签配色 | `success`（`SysNotify.vue` 的 `TYPE_TAG_COLOR`） |

不选 `API`/`CUSTOM_*` 的理由：本平台自身以「接口」为资产，`API` 作渠道码语义自指易混；`HTTP` 与既有 `WEBHOOK` 的差异一眼可辨（协议级 vs 固定报文）。

## 3 `channel_config` Schema（冻结 v1）

存 `notify_channel.channel_config`（varchar(1024)）。

```jsonc
{
  "url":              "https://ops.example.com/api/v1/alarm?cid=${channelId}", // 必填；支持占位符
  "method":           "POST",                    // 可选：POST(默认)/PUT/GET
  "contentType":      "application/json",         // 可选：application/json(默认)/application/x-www-form-urlencoded/text/plain
  "headers":          "{\"Authorization\":\"Bearer ${password}\"}", // 可选：JSON 对象串，值支持占位符
  "bodyTemplate":     "{\"title\":\"${title}\",\"content\":\"${content}\"}",
                                                  // 可选：留空用默认报文 {source,channel,title,content,time}
  "timeoutMs":        5000,                       // 可选：默认 5000，钳制到 [500, 60000]
  "successJsonPath":  "code",                     // 可选：留空 = 仅看 HTTP 状态
  "successJsonValue": "0",                        // 可选：默认 "0"
  "password":         "enc:BASE64密文"             // 可选：唯一加密字段，供 ${password} 占位
}
```

长度实测：含 `enc:` 密文的完整配置约 380–450 字符，varchar(1024) 充裕（`CONFIG_MAX_LENGTH=1024` 超长会在编码层明确报错，不静默截断）。

**读侧别名**：`url` 缺失时回退 `webhook`（前端 `CONFIG_SCHEMA.HTTP.aliases = { webhook: 'url' }` 在编辑回显时归一迁移，值不丢）。

## 4 占位符与转义规则

| 占位符 | 取值 |
|---|---|
| `${title}` | 告警/测试标题 |
| `${content}` | 告警/测试正文 |
| `${time}` | 发送时刻 `yyyy-MM-dd HH:mm:ss` |
| `${channelName}` | 渠道名称 |
| `${channelId}` | 渠道 id |
| `${password}` | **已解密**的渠道密钥（服务层读路径解密后传入） |

可用于 `url`、`headers` 的每个值、`bodyTemplate`。

**转义规则（关键）**：
- `contentType` 为 JSON（subtype 含 `json`）且目标是 `bodyTemplate` 时，替换进去的值做 **JSON 字符串转义**
  （`"`→`\"`、换行→`\n`、控制字符→`\uXXXX`）⇒ 模板写成 `{"msg":"${content}"}` 时，正文含引号/换行也不会把 JSON 打坏；
- `url` 与请求头**一律原样替换**（用于 URL 时请自行 URL 编码或避免特殊字符）；
- **请求头值做 CRLF 清洗**（`\r`/`\n` 剥离），防头注入。

## 5 失败判定（与 T09 铁律一致）

| 场景 | 结果 |
|---|---|
| `channel` 为 null / `channelConfig` 非 JSON / 缺 `url` | `false`，不发起请求 |
| **渠道停用（`status=0`）** | `false`，不发起请求（未发送 ≠ 成功） |
| 请求方法不在 `GET/POST/PUT` | `false` + warn，不发起请求 |
| HTTP 非 2xx | RestTemplate 抛 → catch → `false` |
| 配了 `successJsonPath`：响应非 JSON / 路径取不到 / 值 ≠ `successJsonValue` | `false`（**R5 同类缺陷防线**：HTTP 200 但业务失败不得记为成功） |
| 未配 `successJsonPath` | 2xx 即成功（对端无约定响应体时不凭空制造失败） |
| 任何异常（超时/连接失败/解析失败） | `false`，**永不抛给调用方**（SPI 铁律） |

`successJsonPath` 为点分路径（`code` / `data.ok` / `list.0.id`），由 `HttpApiSender#getByPath` 自实现（行为可控、异常面小、便于覆盖「路径不存在 / 数组越界」分支）。

## 6 超时

- 默认构造用 `SimpleClientHttpRequestFactory` 建 **5s 连接/读取超时**的 `RestTemplate`。
  旧 `WebhookSender` 用裸 `new RestTemplate()`（JDK `HttpURLConnection` **无超时**），外部接口黑洞会挂死
  10s 周期的告警评估线程；新类型不再重复该隐患。
- 渠道 `timeoutMs` 生效时按值缓存实例（`ConcurrentHashMap<Integer, RestTemplate>`），钳制 `[500, 60000]`。
- 注入 `RestTemplate` 的构造（单测用）固定使用注入实例，不启用按渠道超时缓存。

---

## 7 三处同改清单（防「配置了却不发」的假成功）

`NotifySender` 对**无匹配 `ChannelSender` 的类型退化为桩发并返回 `true`**（T08 兼容）。因此新增渠道类型若漏改任一处，
会出现「界面能配、点测试显示成功、实际从未发出」的假成功 —— 本项目的明确缺陷类。

| # | 位置 | 本次改动 |
|---|---|---|
| 1 | 后端 `ChannelSender.supportTypes()` | 新增 `HttpApiSender`，返回 `{"HTTP"}` |
| 2 | 前端 `utils/enum.js` | `ENUM_OPTIONS.channelType` 追加 `{ value:'HTTP', label:'自定义接口' }` |
| 3 | 前端 `SysNotify.vue` | `CONFIG_SCHEMA.HTTP`（canonical/aliases）+ `EMPTY_CONFIG_FIELDS` + 表单分支 + 校验 + `onEdit` 回显 + `canonicalValue` 数值化 + 标签配色 |

验证手段：单测 `NotifySenderTest#httpTypeActuallySends` 以 `verify(exchange)` 锚定真发路径
（只断言返回值会漏掉桩发，因为桩发也返回 `true`）。

## 8 安全

- `password`（接口密钥）**复用 T09 既有链路**，零新增机制：
  写路径 `enc:` 密文落库（FAIL-CLOSED，加密失败拒绝落库）→ 读路径解密（兼容历史明文）→
  响应脱敏（`enc:` 行 → 首4+`****`+末4；明文行 → 固定 `****`）→ 掩码回写防线。
  KEK 仍是 `gatekeeper.crypto.aes-key`（与 app_secret 共用，轮换须同批重加密，方案 R8）。
- 密钥可用于 `${password}` 占位（如 `Authorization: Bearer ${password}`、`X-Token`），
  **只在请求头/请求体/URL 中替换**；日志只打印 `method + url + 响应截断`，不打印密钥与完整报文。
- 请求头 CRLF 清洗；URL/请求头不做转义以保持可预期。

## 9 已知限制与扩展路径（明确记录，不做隐式承诺）

1. **报文只含 title/content**：`NotifySender.send(NotifyChannel, String title, String content)` 的签名冻结
   （T09 约束），**告警等级/来源/指标未进入渠道契约**（`AlarmRuleServiceImpl` 本地算出的 `level`/`source`
   未传入渠道层）。外部系统若需按等级路由，只能解析 `title`/`content` 文本。
   → 扩展路径（需一次 SPI 版本升级）：`ChannelSender` 增加 `send(channel, NotifyPayload)` 重载，
   `NotifyPayload` 携带 `level/source/title/content/extras`；或 `NotifySender` 增重载
   `send(channel,title,content,Map extras)` 并由 HTTP sender 读取。**本次不做**。
2. **GET 不带请求体**（JDK `HttpURLConnection` 不支持 GET 写输出流）：GET 场景请把参数写进 `url` 占位符。
3. **不支持 PATCH**：`HttpURLConnection` 对 PATCH 抛 `ProtocolException` ⇒ 白名单只放 `GET/POST/PUT`，
   其它方法直接 `false` + warn（不产生意外副作用）。
4. **`bodyTemplate` 不做 JSON 合法性校验**（模板里可能有未加引号的占位符，严格 parse 会误判合法用法）；
   仅 `headers` 在**前端**做 JSON 对象校验（后端对非法 JSON 只 warn 并忽略 ⇒ 不校验就是静默失败）。

## 11 环境观察（与本次改动无关，但影响后续探针与演示）

1. **`notify_channel` 现为空表**：T09 §1.2 记录的 4 条种子渠道（id 1–4）已不存在，
   而 7 条种子告警规则仍引用 `channel_ids = '1,3'` ⇒ **这些引用是悬空的**，
   评估命中时 `listByIds` 取不到渠道 ⇒ 通知静默不发（不报错）。
   → 建议：要么补回 4 条种子渠道（注意其 `channel_config` 为空，历史上 `last_test_result='发送成功'`
   系桩发时期的**失真数据**，T09 §3.4 有对应卫生 SQL），要么把种子规则的 `channel_ids` 置空。
   **本次未擅自变更数据。**
2. **`notify_channel` 的自增值曾被复位**：本次探针新建渠道拿到了 id 1/2/3，与种子规则 `channel_ids`
   的字面量撞号 ⇒ 探针清理时 `DELETE /notify-channel/{id}` 被 T07-A 引用完整性检查拒绝（「被 N 条告警规则引用」）。
   这是**产品设计正确行为**（拒绝式优先于级联清理），不是缺陷；探针侧改为 API 失败后按 name 精确 SQL 清理。
3. 探针卫生：`verify_t12_http_channel.py` 结束时渠道数回到基线（0），DB 无残留探针行。
