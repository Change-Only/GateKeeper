### 3.3 换码修正的副作用与裁定（**重点留档**）

**实测发现**：`EXTERNAL_PM` 角色**只持有 `app:credential:create`、不持有 `app:create`**。因此 `POST /app` 由 `app:credential:create` 换为 `app:create` 后，该角色会**失去「新建应用」能力**。

**裁定：换码 + 给 `EXTERNAL_PM` 补授 `app:create`。**

理由：
1. 目标是**修正码的语义错配** —— 「新建应用」本就不该用「新建凭证」的码来保护；
2. 「外部对接人能否新建应用」是**独立的策略决策**，**不应夹带在「修错配」中偷偷完成** —— 否则等于**未经评审就收回一个角色的既有能力**，违反项目「演进式重构：只加不减」原则；
3. **换码 + 补授 = 语义修正 + 零能力回归**。将来若确要收回该能力，**另行评审**。

## 4. 铁律（强制条款，违反即事故）

1. **新增 `@RequirePerm` 的码必须同批 `INSERT IGNORE` 进 `sys_menu` 并插 `sys_role_menu`。**
   - 服务端**无超管通配**，`'*'` **只存在于前端** ⇒ **未播种的码 = 全员永久 403**（含 SUPER_ADMIN / admin）。
   - 只插 `sys_menu`、不插 `sys_role_menu` ≡ **没播**。
2. **种子 SQL 必须幂等**（`uk_menu_perm(perm_code)` + `uk_role_menu(role_id,menu_id)` + `INSERT IGNORE`）；**改完必须 `DEL gk:perm:*`**（Redis 权限缓存 TTL 24h，否则表现为「播了却仍 403」）。
3. **收尾必跑红线校验**：**后端注解集合 ⊆ 播种集合，越界数必须为 0**。这是 T05 的成果，**本轮不得破坏**。
4. **不要顺手改既有码的 `risk_flag`** —— 会波及前端**高危标记展示**，属无收益的连带变更。

## 5. 验收判据（必须可执行）

1. **回归基线**：`mvn -o test` **全绿**（T08 前基线 **374** 用例：`Tests run: 374, Failures: 0, Errors: 0, Skipped: 0` → BUILD SUCCESS）。
2. **红线校验**：后端注解集合 ⊆ 播种集合，**越界数 = 0**。
3. **权限生效性验证（核心，不可省略）**：
   - 用**不具备该码的低权限角色**调用新加注解的端点 ⇒ **期望 403**；
   - 用 **admin** 调用 ⇒ **期望 200**。
   - **仅「编译通过 / 测试通过」不算完成** —— 那只能证明代码能跑，不能证明权限生效。
4. **前端闸门验证**：对应按钮加 `PermButton` 闸门后，**无权限角色看不到该按钮**。
5. **反向验证（防过度收紧）**：`EXTERNAL_PM` 在「换码 + 补授 `app:create`」后，**仍可新建应用**（验证零能力回归）。

> **方法纪律（承 T07）**：本类属**语义型缺陷**，必须用**能失败的用例**验收 —— 即「低权角色期望 403」这种**反向断言**。只验「接口返回 200 / 页面能打开 / 编译通过」，对此类缺陷是**绿灯漏检**。
