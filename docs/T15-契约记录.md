## 1 分组加解密配置（需求一）

### 1.1 为什么是「三态」而不是布尔

老表 `api_interface.request_encrypted` 是 boolean（开/关两态），无法区分需求要求的「**下级继承上级**」与「**显式不要加解密**」：

| 场景 | 布尔列能否表达 |
| --- | --- |
| 下级未配置，随上级 | ❌（`false` 既可能是"没配"也可能是"显式不要"） |
| 下级显式关闭，**且不许回退到应用级** | ❌ |

因此新表用 `mode` 三态列。

### 1.2 表 `api_group_encryption_config`

| 列 | 说明 |
| --- | --- |
| `id` | 主键 |
| `group_id` | 接口分组 id，**唯一键 `uk_gec_group(group_id)`** |
| `mode` | `INHERIT` / `ENABLED` / `DISABLED`，默认 `INHERIT` |
| `algorithm` | 算法（`ENABLED` 时必填） |
| `secret_key` | 密钥 |
| `created_at` / `updated_at` | 时间戳 |

**刻意不加的列**：
- **无 `env_code`** —— 加解密是**接口契约**，不分环境（与 `api_group_env_config` 的取舍不同）。
- **无 `version`** —— 无灰度需求。

### 1.3 生效优先级（唯一口径 `gateway/EncryptionConfigResolver`）

```
接口级（api_interface.request_encrypted，存在即终止，保留老语义）
  > 分组级（沿 parent_id 上溯；INHERIT 继续上溯，ENABLED/DISABLED 命中即终止）
    > 应用级
```

- `EnvConfigResolver` 范式：`visited` 集防环 + `MAX_GROUP_DEPTH=32` + 回传 `sourceType` / `sourceGroupId` / `sourcePath`。
- **网关转发**与**前端只读预览**共用同一解析结果 ⇒ 避免「页面显示继承 A、网关走 B」。

### 1.4 语义边界

- `INHERIT`：等价「未配置」，**继续上溯**（不是"使用父值后停止"）。
- `ENABLED`：命中即终止，采用本行算法与密钥。
- `DISABLED`：命中即终止，**且不回退应用级**；密钥**不透出**（`/own` 接口不得出现幽灵密钥）。

### 1.5 写入契约

**先删后插（全量覆盖）**：`updateById` 的 NOT_NULL 策略写不进 `null`，若 `mode` 改回 `INHERIT` 而 `algorithm`/`secret_key` 置空会残留旧值 ⇒「界面看着关了加密、库里还留着旧密钥」的幽灵数据。

### 1.6 端点与权限

路径前缀 `/api-group-encryption`：

| 端点 | 权限点 | risk |
| --- | --- | --- |
| `GET  /api-group-encryption/effective?groupId=` | （只读，**不加注解**） | — |
| `GET  /api-group-encryption/own?groupId=` | （只读，**不加注解**） | — |
| `POST /api-group-encryption/upsert?groupId=` | `api_group_encryption:create`（id 356） | 1 |
| `PUT  /api-group-encryption/{id}` | `api_group_encryption:update`（id 357） | 1 |
| `DELETE /api-group-encryption/{id}` | `api_group_encryption:delete`（id 358） | 1 |

- `/effective` 返回**沿分组树向上继承后的生效配置**（同网关口径，含 `sourceType`/`sourceGroupId`/`sourcePath`）；无配置返回 `data=null`（回落应用级）。`/own` 只回本分组自己那一行（**不含继承**）。
- 两查询端点**不加 `@RequirePerm`**（只读，运维/审计也要看分组是否加密）。
- 写端点全部 `risk = true`（加解密变更属高危）。
- 授权按**同语义既有权限点**（`api_group:create/update/delete`）持有角色动态推导（各 5 个角色）。

## 2 双层访问白名单（需求四）

### 2.1 为什么是两层

需求「**系统访问白名单在应用设置中可配置**」有两种解读，用户明确要求**两者都做**：

| 层 | 表 | 语义 | 是否参与网关校验 |
| --- | --- | --- | --- |
| 应用级 | `app_ip_whitelist` | 某应用的调用方可信 IP | ✅（按 `status=1` 过滤） |
| 系统级 | `sys_ip_whitelist` | 整个平台的可访问 IP 白名单 | ✅（网关最前一环） |

### 2.2 应用级：修「停用条目仍在拦人」

- DDL 早有 `env_code`(默认 `'prod'`) / `status`(默认 `1`)，但**实体未映射、`IpWhitelistHandler` 不过滤 `status`** ⇒ 停用条目仍生效。
- 本轮：实体补字段 + Handler 加 `.eq("status", 1)` + 前端配置项（环境/状态列、启停、编辑）。
- 新增 `PUT /app/ip-whitelist/{id}`（权限 `app:ipwhitelist:update`，id 359，risk=1，授权继承 `app:ipwhitelist:add` 持有角色）；归属应用**不可改**。
- 🔴 `env_code` = **归类标注维度，不参与网关校验**（白名单强语义，误拦代价远高于误放）。

### 2.3 系统级：`SysAccessWhitelistHandler`（`@Order(0)`，网关最前一环）

| 情形 | 行为 |
| --- | --- |
| 表空 / 无启用行 | **不限制**（SQL 刻意不播种任何行 ⇒ 对存量环境零影响） |
| 命中 | 放行 |
| 未命中 | 拦截（`IP not in system whitelist`） |
| **查询异常** | **fail-open 放行 + WARN**（基础设施抖动不应把全站打死） |

- CIDR 写入侧用**正则**校验：`InetAddress` 会把 `localhost` 这类主机名解析成地址而误"通过"，但白名单存主机名运行期永不匹配来源 IP（等于永不生效）。前缀范围：IPv4 `0-32` / IPv6 `0-128`。
- 写端点**复用既有 `sys:security:update`**（避开「新增码忘授权 ⇒ 连 SUPER_ADMIN 都拿不到」）。
- 只读 list/GET 沿仓库约定**不加 `@RequirePerm`**（`AppController` 全部 list/GET 均无注解，单点加反而让缺码角色一打开页面就 403）。

### 2.4 网关责任链 Order（现行）

```
0 SysAccessWhitelistHandler(新) -> 1 AppAuthHandler -> 2 IpWhitelistHandler
-> 3 IpBanCheckHandler -> 4 RateLimitHandler -> 5 PermissionHandler
-> 6 EncryptionHandler / VersionRouteHandler -> 7 AbnormalParamCheckHandler
-> 8 ForwardHandler -> 9 LogHandler
```

## 5 本轮的环境级坑（工程经验，非契约）

### 5.1 🔴 `mvn -o test` 全绿 ≠ 应用能启动

- Maven 增量编译「删 `.java` 不删 `.class`」：T15-6 删除 `BizLine*` 源码后 `target/classes` 残留 4 个孤儿类（`BizLineController` / `BizLineDto` / `BizLine` / `BizLineMapper`）。
- 单测 **590 条全绿未暴露**；重启应用才崩 `NoClassDefFoundError: com/gatekeeper/service/BizLineService`（`bizLineController` bean 实例化失败）。
- 修法：`_gk_db_check/prune_stale_classes.py` 扫描 `target/classes|test-classes/com/gatekeeper` 下孤儿类并删除。
- ⇒ **删除任何 Java 源码后，必须跑一次孤儿 class 扫描再启动验证。**

### 5.2 其它

- `.gitignore` 的 `/_*.py` 只匹配「下划线开头的**文件**」、**匹配不到目录** ⇒ `_gk_db_check/` 长期 untracked；补 `/_gk_db_check/` 目录口径。
- `ip_ban` 表的 IP 列名是 **`ip_address`**（不是 `ip`）；探针写错抛 `(1054, Unknown column 'ip')`，被 best-effort 吞掉 ⇒ 表现为「解禁静默失败」。
