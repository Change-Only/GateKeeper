## 0. 结论摘要

**一句话**：这个系统的"防护面"（签名、防重放、加密、注入防御）实现质量明显高于同类项目；但"授权面"是**默认允许**而非默认拒绝 —— **212 个端点中 100 个（47%）后端无任何权限校验**，其中包括 10 个写操作端点，攻击者可用一个最低权限账号关闭封禁、关闭告警、改写加密配置、无限延长接口授权。同时，`SecurityStartupCheck` 这一"最后一道防线"被自身配置里的默认值绕过。

| 严重级 | 数量 | 主题 |
|---|---|---|
| 🔴 P0 | 6 | 授权默认放行（根因）、延期授权绕过、安全防护可被注销、加密配置可被改写、主密钥明文入库、**调用报文可被任意账号全量读取导出** |
| 🟠 P1 | 9 | 密钥自检失效、网关 SSRF、会话与权限撤销不即时、通知渠道 SSRF、ECB 落库、登录锁定可被武器化、**口令散列泄漏**、**默认口令 123456**、**数据权限从未实现** |
| 🟡 P2 | 9 | 文档免认证暴露、陈旧依赖、内网地址入库、固定口令种子、错误回显、CORS 组合风险、短密钥掩码、**环境配置无掩码（内网拓扑暴露）**、**`@RequirePerm` 空值 fail-open** |

**风险优先级建议**：P0-1 是根因，应先收紧拦截器默认策略（改动量小、收益最大），再逐个补齐 10 个写端点的注解。

## 1. 审计范围与信任边界

### 1.1 资产清单

| 层 | 组件 | 说明 |
|---|---|---|
| 入口 1 | `/api/gateway/**` | 网关代理，**不走 JWT**，用 AppKey + 签名鉴权（`WebConfig:46` 显式放行） |
| 入口 2 | `/api/**`（其余） | 管理后台，JWT 认证 + `@RequirePerm` 授权 |
| 入口 3 | `/doc.html`、`/v3/api-docs/**` | Knife4j 接口文档，**免 JWT 免授权**（`WebConfig:47-51`） |
| 数据 | MySQL `gatekeeper`（42 表）+ Redis | 主数据：接口资产 / 应用身份 / 授权关系 |
| 密钥 | `application.yml` 默认值 → `GATEKEEPER_*` 环境变量 | JWT 签名密钥、落库 KEK、DB 口令 |

### 1.2 关键架构事实（已核实，非推测）

1. **未引入 Spring Security**（`pom.xml` 无 `spring-boot-starter-security`），认证与授权全部自研。
2. 认证 = `config/JwtAuthInterceptor.java`（**只验令牌，不查数据库用户状态**）。
3. 授权 = `security/PermissionInterceptor.java`，**仅对带 `@RequirePerm` 的 handler 生效**，第 64-67 行对无注解者**直接放行**，注释写明「兼容存量」。
4. 项目有成文设计口径：`docs/backend-补课-合同.md:33` —— 「仅对**高危写操作**加 `@RequirePerm`；读操作与低危写操作**不强制**（页面可见性已通过菜单 perm 控制）」；同文件 R5 预留了审计接口：「若安全审计要求读也鉴权，需统一调整切面」。

> 因此本报告对"读端点无注解"**不作为缺陷计数**（属既定策略），但在 §2.1 指出该策略在 10 个写端点上的**具体后果**，并说明"页面可见性"不构成访问控制。

## 2. 🔴 P0 发现

### P0-1 授权模型默认放行：47% 端点无后端权限校验，含 10 个写操作

**位置**：`security/PermissionInterceptor.java:64-67`（根因）；各 Controller（暴露点）

```java
RequirePerm requirePerm = methodAnnotation != null ? methodAnnotation : classAnnotation;
if (requirePerm == null) {
    // 无注解 → 不拦截（兼容存量）
    return true;
}
```

**全量比对结果**（脚本口径：仅统计方法级 mapping，已排除类级 `@RequestMapping`）。
下表为**独立复核轮重算后的修正值**（初版曾少计 8 个端点）；**09-24 又以严格口径做了第三轮复算，端点总数与无注解数再各修正 +6**（详见 附录 C 末行与 附录 D）：

| 指标 | 数值 |
|---|---|
| Controller 文件 | 31 |
| 方法级端点 | **212** |
| 受 `@RequirePerm` 保护 | **112（53%）** |
| **无任何权限注解** | **100（47%）** |
| └ 其中**写操作**（POST/PUT/DELETE） | **11**（含 `/auth/login`，实质 10 个） |

**两路交叉校验（09-24 严格口径复算，修正下图算式）**：① 全量 mapping 注解行 **237**，其中类级 `@RequestMapping` **25** 个 —— ⚠️ **不是 31**：31 是「含 mapping 注解的 Controller 文件数」，而其中 **6 个控制器根本没有类级前缀**（`AppController` / `DashboardController` / `EncryptionConfigController` / `InterfaceController` / `InterfaceProtectionController` / `PermissionController`，它们把绝对路径直接写在方法上），故**方法级端点 = 237 − 25 = 212**；② 全仓 `@RequirePerm` 注解行恰 **112**，与 112 个受保护端点**一一对应** —— 复算确认**孤立注解 0**（每个注解都挂在 mapping 方法上；源码注释中的 15 处 `@RequirePerm` 提及已按注解语法排除，不计入）。另确认：项目**不存在类级 `@RequirePerm`** —— `PermissionInterceptor.java:61` 虽保留了 `getBeanType()` 的类级读取能力，但无任何 Controller 使用它。

> ⚠️ **扫描陷阱（复核时踩到，留档以免复发）**：`controller/AppController.java:94` 的 Javadoc 里写了"刻意不加 `@RequirePerm`"字样，**子串扫描会把它误判为「受保护端点」**。必须按注解语法匹配，不能只搜字符串。（09-24 次轮复算中同类陷阱再现：源码注释里另有 15 处 `@RequirePerm` 字样，若不排除会让受保护端点数从 112 虚增到 115。）
>
> 🔧 **09-24 勘误**：本节此前写作 `237 − 31 = 206`，**减数用错** —— 31 是文件数而非类级注解数，导致端点总数、无注解数各**少计 6**。修正后的权威值见上表（212 / 112 / 100）。修正过程与三方口径对照见 **附录 D**。
>
> 📌 **统计口径声明**：`controller/GatewayController.java:54` 的 `@RequestMapping(method = {GET, POST, PUT, DELETE})` 同样无注解且接受写动词，但它是**数据面入口**（由 `GatewayCore` 做 AppKey + 签名鉴权），不属于管理面授权缺口。若按纯 HTTP 动词口径统计，"无注解写端点"会变成 12 —— 本报告统一以**管理面**为准，不计入数据面入口。

**对比证据（同一文件内相邻方法的注解不一致，证明是遗漏而非设计）** —— `grant/GrantController.java`：

```java
@RequirePerm(value = "grant:create",  risk = true) @PostMapping("/create")   // ✅ 61-63
@RequirePerm(value = "grant:approve", risk = true) @PostMapping("/{id}/approve") // ✅ 68-70
@RequirePerm(value = "grant:reject",  risk = true) @PostMapping("/{id}/reject")  // ✅ 75-77
@RequirePerm(value = "grant:revoke",  risk = true) @PostMapping("/{id}/revoke")  // ✅ 82-84
@Operation(summary = "延期授权")                    @PostMapping("/{id}/renew")   // ❌ 89-90 无注解
```

**可利用性**：攻击者只需一个**任意权限的合法账号**（例如只读账号），用 curl 直接打端点即可，**不经过前端页面**。前端"菜单可见性"完全不构成防护。

**修复方案**：

1. **立即（改一行，堵住面）** —— 把拦截器默认策略从"放行"改为"拒绝"，用白名单显式放行只读端点：

```java
// PermissionInterceptor.preHandle
if (requirePerm == null) {
    // 默认拒绝：仅放行显式登记为「公开只读」的端点
    String key = request.getMethod() + " " + request.getRequestURI().substring(contextPath.length());
    if (PUBLIC_READ_ENDPOINTS.contains(key)) {   // 集中维护的只读白名单
        return true;
    }
    log.warn("Blocked un-annotated endpoint: {} {}", request.getMethod(), request.getRequestURI());
    reject(response, 403, "该接口未登记访问策略，已拒绝");
    return false;
}
```

> ⚠️ **上面那段示例是方向示意，不要照抄**（09-24 实测修正）：把 100 个无注解端点里的 89 个只读端点全部列入 `PUBLIC_READ_ENDPOINTS`，与「默认放行」**安全等价** —— 白名单等于把默认值抄了一遍，没有安全收益，却新增了「漏列即 403」的回归风险。**可行做法是按 HTTP 动词分治**：
>
> ```java
> // 可行版本：无注解时按 HTTP 动词判定
> if (requirePerm == null) {
>     if (WRITE_METHODS.contains(request.getMethod())
>             && !isPublicWriteEndpoint(request)) {   // 仅放行 POST /auth/login 等极少路径
>         reject(response, 403, "该写接口未登记访问策略，已拒绝");
>         return false;
>     }
>     return true;   // 只读仍放行（读侧收敛待后续单独完成）
> }
> ```

2. **然后（逐个补齐）** —— 为 §2.1 表格中 10 个写端点补 `@RequirePerm`，码值复用同域既有码、不新增（示例）：
   - `POST /grant/{id}/renew`、`POST /permission/{id}/renew` → **`grant:approve`**（延期实质是"重新批准有效期"，与审批同风险级）
   - `POST /block-rule/{id}/toggle`、`PUT /block-rule/{id}/update` → 复用 `block_rule:update`
   - `POST /alarm-rule/{id}/toggle`、`PUT /alarm-rule/{id}/update` → **`alarm_rule:create`**（从"可关告警"看，风险等同创建）
   - `POST /encryption/*` → **`api:env:update`**
   - `PUT /alert/*/read` → `alert:read`（新增或复用）

3. **前端对齐** —— 同期补闸门，例如 `views/perm/PermMatrix.vue:141` 的「续期」按钮当前仅为 `v-if="row.status === 1"`，需改为 `v-if="row.status === 1 && hasPerm('grant:approve')"`。

**验证方式**：用最低权限账号（如仅 `log:call:list`）curl 上述端点，改前应为 200/成功，改后应为 403；并确认原本可用的只读端点仍为 200（防过度收紧）。

### P0-2 延期授权无权限 —— 直接绕过"授权到期"这一唯一时间防线

**位置**：`grant/GrantController.java:89-93`、`controller/PermissionController.java:143-148`

```java
@Operation(summary = "延期授权")
@PostMapping("/{id}/renew")
public Result<AppApiGrant> renew(@PathVariable Long id, @Valid @RequestBody GrantRenewRequest req) {
    return Result.success(grantService.renew(id, req.getValidTo()));   // validTo 由请求体完全控制
}
```

**影响**：平台的授权模型是 Default Deny + 有效期控制（`app_api_grant.status=1` 且 `validFrom <= today <= validTo`，`GrantExpireJob` 每日 02:00 批量置为过期）。`renew` 把 `validTo` 交给请求体任意指定 ⇒ **任何登录用户可将任意一笔"即将到期/已延长过"的授权无限续期**，使到期机制、`GrantExpireJob`、网关的双保险全部失去意义。

**放大条件**：`GET /grant/list`、`GET /grant/pending`、`GET /permission/pending` 同样无权限注解 ⇒ 攻击者可先枚举出所有授权 ID 及其到期日，再有选择地续期（**外部攻击者视角：可让已撤销之外的全部授权永久有效**）。

**修复方案**：同 P0-1 第 2 条（补 `grant:approve`）。另外建议在服务层加**业务约束**，不依赖单一权限点：
- `validTo` 不得为空、不得早于当前 `validTo`（防"缩短后伪造"）、单次延期上限（如 ≤365 天）、累计延期上限；
- 延期必须写 `api_change_log` / 审计日志（当前 `renew` 未走 `@ApiChangeLog`）。

**验证方式**：单测新增 3 例（越权续期应 403 / `validTo` 早于现值应 400 / 超上限应 400），并在 `PermMatrix` 页用双身份差分确认按钮可见性变化。

### P0-3 安全防护可被静默注销（封禁规则 / 告警规则的启停与修改无权限）

**位置**：`BlockRuleController.java:81,93`、`AlarmRuleController.java:94,106`、`AlertController.java:77,89`

**影响链**：这是**攻击者做完整入侵所需的最后一块拼图**。系统所有入侵痕迹都产出告警（5 类安全检测器 → `security_event` → 告警规则 → 通知渠道）。攻击者拿到任意一个账号后可：
1. `POST /block-rule/{id}/toggle` 关闭自动封禁 → 后续高频爆破不再被封；
2. `POST /alarm-rule/{id}/toggle` 关闭告警规则 → 不再产生通知；
3. `PUT /alert/read-all` 清空未读 → 运维失去感知。

三者叠加 = **在被告警系统"合法地"静音的前提下持续攻击**。

**修复方案**：补注解（同 P0-1），并追加两条纵深防御：
- **关键防护对象的启停强制审计**：`block_rule` / `alarm_rule` 的 toggle 走 `@ApiChangeLog` 或写入 `sys_operation_log`（高危操作必须留痕，且**不允许被静默**）；
- **兜底告警**：当"封禁规则全停用"或"告警规则全停用"时，由后台任务直接产生一条 `CRITICAL` 通知（不经过规则引擎，防止"关规则即无告警"的自锁）。

**验证方式**：curl 低权限账号调 toggle → 403；管理账号调 toggle → 成功且 `sys_operation_log` 新增一行。

### P0-4 平台加解密配置可被任意登录用户改写

**位置**：`controller/EncryptionConfigController.java:54-59、81-86`（**整个类 5 个端点全部无 `@RequirePerm`**）

```java
@Operation(summary = "保存接口加密配置")
@PostMapping("/interface")
public Result<Void> saveInterfaceConfig(@RequestBody ApiEncryptionConfig config) {
    apiEncryptionConfigService.saveConfig(config);   // 算法 / 密钥 / 开关 全部来自请求体
    return Result.success();
}
```

**影响**：请求体直接反序列化为配置实体并落库，**无参数校验、无归属校验、无权限校验**。攻击者可：
- 将模式置为 `DISABLED` ⇒ 该接口/应用的请求体与响应**明文传输**（含用户敏感字段）；
- 写入**自己已知的密钥** ⇒ 中间人可解密并伪造报文。

**修复方案**：
1. 补 `@RequirePerm("api:env:update")`（与 `ApiEnvConfigController` 同域风险级）；
2. 服务层加**输入校验**：算法白名单（仅允许 AES-256-CBC / SM4）、拒绝空密钥与过短密钥、拒绝在请求体里明文提交密钥（改为写入后仅回显掩码）；
3. 该接口属历史遗留（新链路是 `ApiGroupEncryptionConfigController` / `InterfaceProtectionController`）—— 若已确认无前端调用，建议**直接下线该 Controller**，减少攻击面（符合"演进式重构"中的"不保留无主入口"）。

**验证方式**：`grep -rn "encryption/interface" src/frontend/src` 确认前端引用；有引用则补权限后回归，无引用则删除并回归 773 用例。

### P0-5 落库主密钥（KEK）明文入库

**位置**：`docs/T17-契约记录.md:50`（**已被 git 跟踪**）

```
- 密钥：复用落库 KEK `gatekeeper.crypto.aes-key`（`application.yml` 默认
  `<已脱敏:41位AES-KEK>`），经 `CryptoKeyUtil.toBase64Key` 规范化为 32 字节。
```

**取证（用 `git grep` 只搜被跟踪文件，排除"仅本地存在"的误判）**：

| 密钥 | 在被跟踪文件中命中 |
|---|---|
| `<已脱敏:41位AES-KEK>`（AES KEK） | **✅ 1 个文件：`docs/T17-契约记录.md:50`** |
| JWT 签名密钥（49 位） | 0 |
| DB 口令（22 位） | 0 |

**旁证**：`.gitignore:41` 已把 `application.yml` 排除，注释写明「主配置含真实密钥（DB/AES/JWT），永不入库」—— 即项目**已经意识到**这个问题并处理了配置文件，但**文档里同一把密钥漏了**。

**泄漏面收窄（独立复核轮补充）**：复核确认被跟踪的 `application.example.yml` **不含**该密钥值，`application.yml` 自身也未被跟踪 ⇒ 本项泄漏**仅限 `docs/T17-契约记录.md` 一处、一行**，而非「仓库里到处都有」。这降低了紧迫度但**不改变结论**：该值已随 git 历史分发，仍须轮换。

**影响**：这把 KEK 是**全库密文的唯一钥匙**——`app_secret`、接口路径/参数（T17）、通知渠道密码（T09）都用它（或与它同源）加密。拿到仓库 = 拿到钥匙 ⇒ 若同时拿到数据库备份/只读账号，全部密文即刻还原。

**修复方案（三步，必须按序）**：

**验证方式**：低权限账号 curl `/api/log/list`、`/api/log/1` 应 403；有权限账号验证列表仍正常（防过度收紧）；抽样检查新落库的 `api_call_log.request_params` 中敏感键已掩码。

### P1-2 网关转发 SSRF：目标地址无白名单、无内网/元数据拦截

**位置**：`gateway/handler/ForwardHandler.java:124,145-150`

```java
String backendUrl = ctx.getBackendUrl();     // 源自 api_interface.backend_url / api_env_config.backend_url
...
response = restTemplate.exchange(backendUrl, HttpMethod.valueOf(ctx.getMethod()), entity, String.class);
```

**核实结果**：全仓**未发现**任何主机白名单、私网地址（`127.` / `10.` / `172.16-31` / `192.168.` / `169.254.169.254`）拦截逻辑；`HttpClientConfig` 与 `ForwardHandler` **均未显式设置重定向策略**（全仓 `setRedirectStrategy` 命中 **0**），因此使用 HttpClient 默认策略（会跟随 GET/HEAD 的 301/302/307）。

**影响**：
- **写权限者 → 内网探测**：拥有 `api:update` / `api_env_config:*` 写权限者（本报告 P0-1 已说明大量写端点缺权限）可把 `backend_url` 指向内网任意地址，借网关做**内网端口扫描与服务探测**（响应体经网关原样返回给调用方）；
- **云环境升级为凭证窃取**：若部署在公有云，`http://169.254.169.254/latest/meta-data/iam/security-credentials/` 可经网关取回**实例角色临时凭证** ⇒ 接管云账号。**此时应升级为本报告最高优先级**；
- **重定向绕过**：即便后续加了朴素的主机白名单，跟随重定向可使请求跳到非白名单地址。

**修复方案**：
1. 在 `ForwardHandler` 转发前统一做**目标地址校验**（新建 `UpstreamAddressGuard`）：
   - DNS 解析后校验 IP 是否属私网/回环/链路本地/组播/保留段（含 IPv6 的 `::1`、`fc00::/7`、`fe80::/10`），**解析后校验**而非校验字符串（防 DNS rebinding 与十进制 IP 绕过）；
   - 云元数据地址（`169.254.169.254`、`metadata.google.internal`）**硬拒绝**；
   - 需要访问内网的场景改为**显式白名单**（`api_env_config` 增加"允许的主机后缀"字段，或引入配置项 `gatekeeper.gateway.allowed-hosts`），默认空 = 只允许公网。
2. **关闭自动重定向**：`HttpClientConfig` 中显式 `setRedirectStrategy(new LazyRedirectStrategy())` 或禁用；如需跟随，则对每一跳重复第 1 步校验。
3. 同类面一并加固（见 P1-4）。

**验证方式**：单测覆盖 8 类地址（`127.0.0.1`、`10.0.0.1`、`192.168.1.1`、`172.20.0.1`、`169.254.169.254`、`[::1]`、十进制 IP `2130706433`、内网域名解析后为私网）→ 全部拒绝；公网地址 → 放行。

### P1-3 会话与权限撤销不即时（最长 120 分钟的"僵尸会话" + 24 小时权限滞留）

**涉及三处，可叠加**：

1. **`/auth/logout` 不实现吊销** —— `AuthController.java:37` 注释明示「前端清除令牌即可，此处预留审计扩展」。JWT 无服务端状态，登出后**令牌仍然有效直至 `exp`**。
2. **认证拦截器不查用户状态** —— `JwtAuthInterceptor.java:46-55` 只解析令牌并取 `uid`，**不校验用户是否已被停用/删除**。因此 `PUT /system/user/{id}/status/0`（停用）与 `DELETE /system/user/{id}`（删除）**对已登录会话无任何效果**。
3. **权限缓存 TTL 24 小时** —— `PermissionCacheService.java:56`（`CACHE_TTL_HOURS = 24`），且 `PermissionInterceptor` 每次请求只读该缓存。

**量化**：`gatekeeper.jwt.expire-minutes: 120`（`application.yml:106`，已被 `JwtUtil:25` 真实读取）。故**停用/降权一个用户后，其令牌最长再有效 120 分钟，权限最长滞留 24 小时**。

> 附带发现（同一文件）：项目长期记忆中的运维纪律「改完权限种子必须 `DEL gk:perm:*`」正是本问题的**人工补偿**。代码里的失效机制 `replaceUserRoles`（用于"给用户分配角色"）**没有任何 Controller 调用**（`SysUserServiceImpl` 的 `updateUser` 也不处理角色），即"用户-角色分配"功能未接线、只能改库。

**修复方案**：
1. **缩短有效窗口**：`gk:perm` TTL 从 24h 降到 5-10 分钟（权限点集合很小，回源 DB 成本低）；`PermissionCacheService` 已实现"缓存未命中回源"，无功能风险。
2. **令牌吊销**：引入 Redis 黑名单（`gk:jwt:revoked:{jti}`，TTL = 剩余有效期），`/auth/logout` 写入；`JwtAuthInterceptor` 校验黑名单。
3. **登录态校验用户状态**：`JwtAuthInterceptor` 中按 `uid` 读用户（可复用 5-10 分钟的短缓存），状态非 1 或已删除 ⇒ 401。
4. **停用/删除时主动失效**：`SysUserServiceImpl.updateStatus` / `deleteUser` 调用 `permissionCacheService.invalidateUser(id)` + 写吊销标记（该服务已具备能力，缺的只是调用）。
5. **接线"用户-角色分配"**：让 `SysUserServiceImpl.updateUser` 调用现成的 `replaceUserRoles`（含 afterCommit 失效），或在 `SystemController` 增加端点。

**验证方式**：E2E —— 用户 A 登录 → 管理员改 A 的角色 → 立即用 A 的旧令牌访问新权限端点应 403；管理员停用 A → A 的令牌应立即 401（而非等 2 小时）。

### P1-5 落库加密使用 AES/ECB（确定性密文、无完整性保护）

**位置**：`app_secret`、通知渠道密码的落库加解密；T19 已把 `sys_config['secret.encrypt.algo']` 更正为 `AES/ECB/PKCS5Padding`，即**确定了 ECB 就是现实**。

**影响**：
- **无 IV ⇒ 确定性**：相同明文永远产生相同密文。攻击者拿到库（或只读账号）可对 `app_secret` 等做**等值比对/字典攻击**（低熵密钥可被批量还原），并观测到"哪些应用共用同一密钥"；
- **无完整性校验**（无 MAC/AEAD）⇒ 密文可被篡改（配合 CBC 的 padding oracle 类攻击；ECB 下则表现为可控的块替换）。

**对照**：T17 的新链路（`InterfaceCryptoService`）做得**很好** —— `enc:v1:<iv>:<cipher>`、**每次随机 16 字节 IV**、CBC。问题只在**老的落库链路**。

**修复方案**：
1. 统一改用 `AES-256-CBC` + 随机 IV（复用 T17 已验证的 `CryptoKeyUtil` + 格式），密文加版本前缀（如 `enc:v2:`），**读路径双格式兼容**（存量 `enc:` 与无前缀明文照旧可读）；
2. 迁移脚本一次性重加密（与 P0-5 的 KEK 轮换**合并到同一次维护窗口**，避免两次全库重写）；
3. 长期建议引入 AEAD（`AES-GCM`）以获得完整性保护。

**验证方式**：同一明文加密两次密文不同；旧格式数据仍可解密；`mvn -o test` 全绿。

**核实结果**：全仓**无验证码**实现（关键词 `captcha`/`Captcha`/`验证码` 命中 0）；无按 IP/全局的登录限速。

**影响**：
- **账号锁定 DoS**：攻击者只需对管理员用户名**故意失败 5 次**，即可把该管理员锁定 10 分钟；循环执行即可让**所有管理员永久无法登录**（而系统正是要靠管理员登录才能处置攻击）；
- **键污染**：锁定键在用户名校验**之前**生成，不存在的用户名也会在 Redis 留下键（内存增长面）；
- **密码喷洒可行**：无 IP 限速与验证码，攻击者可对**大量用户名各试 2-3 次**（低于 5 次阈值）横向喷洒常见弱口令，且不触发任何锁定。

**修复方案**：
1. 锁定维度改为 **`username + clientIp` 双维度**：单 IP 失败计数（如 20 次/10 分钟 → 拒绝该 IP）、单账号计数（保留现值，但**仅对已存在的用户名**计数）；
2. 密码喷洒缓解：增加**全局登录速率限制**（如 100 次/分钟/整个系统）与失败响应的**固定延迟**（如 300ms，削弱枚举与爆破吞吐）；
3. 管理后台登录建议加**验证码**（连续失败 3 次后出现）；
4. Redis 异常时不要 500：`get/increment` 包 try/catch，降级为"仍允许登录但记录 ERROR"（避免 Redis 抖动导致管理后台整体不可登录）。

**验证方式**：单测/手工 —— 5 次错误密码后，**另一个 IP** 用正确密码应能登录（证明锁定不再可被第三方利用）；不存在的用户名不应产生 `login_fail:*` 键。

### P1-7 用户列表泄漏 BCrypt 口令散列（配合默认口令 ≈ 提权）

**位置**：`entity/SysUser.java:23` + `application.yml:55` + `controller/SystemController.java:67`

```java
public class SysUser {
    private Long id;
    private String username;
    private String password;      // 第 23 行 —— 无 @JsonIgnore
    ...
}
```

`application.yml:55` 显式设置了 `spring.jackson.default-property-inclusion: always`（为了修复另一处 `NULL` 被吞的问题），意味着**null 与所有字段都会下发**。

**取证**：`grep 'password|JsonIgnore' SysUser.java` 输出中**只有 `private String password;`，没有任何 `@JsonIgnore`**；而 `SysUserServiceImpl.pageQuery`（`:31-38`）走 `selectPage` 直接返回实体。对比：`createUser:58` 与 `updateUser:71` 都做了 `user.setPassword(null)` 的防御 —— 说明开发者知道要遮蔽，**只是列表查询这一条路径漏了**。

**影响**：`GET /api/system/user/list` 无权限注解 ⇒ **任何登录用户可拿到全部用户的 BCrypt 散列**（`$2b$10$...`，cost=10）。结合 P1-8（新建用户默认口令 `123456`）与 `sql/init.sql:878` 的固定种子散列，攻击者可直接离线比对/爆破出可登录口令 ⇒ **从任意账号提升为管理员**。

**修复方案**：
1. `SysUser.password` 加 `@JsonProperty(access = JsonProperty.Access.WRITE_ONLY)`（**一处修复覆盖所有出参路径**）。
   ⚠️ **不可用 `@JsonIgnore`**（09-24 实测修正）：它会同时禁掉反序列化，而登录／建号／改密都需要从请求体读入 `password`，照此改会破坏这三条链路。
2. 出参改为专用 VO（`SysUserVo`）而不是直接返回实体 —— 与项目既有约定「列表 VO ⊇ 实体全部可编辑字段」一致，同时避免未来再漏字段；
3. 该端点同时补 `@RequirePerm("sys:user:list")`（若已播种则复用）。

**验证方式**：`curl /api/system/user/list` 的响应 JSON 中 `password` 字段应不存在或为 null；`mvn -o test` 全绿。

### P1-8 新建用户默认口令硬编码为 `123456`，且无强制改密

**位置**：`service/impl/SysUserServiceImpl.java:49-58`

```java
public SysUser createUser(SysUser user) {
    user.setPassword("123456");                            // 默认初始密码（硬编码，忽略入参）
    ...
    user.setPassword(BCrypt.hashpw(user.getPassword()));   // BCrypt 加密存储
    ...
    user.setPassword(null);                                // 清除密码避免返回给前端
```

**影响**：管理员新建的每个账号初始口令都是 `123456`，且代码**显式忽略**了请求体里传入的口令。系统**无"首次登录强制改密"机制**（无 `password_changed_at` / `must_change_password` 字段）。配合 P1-7 的散列泄漏与 P1-6（可对任意用户名锁定/无验证码），形成完整攻击链：**读散列 → 确认是 `123456` → 直接登录**。

**修复方案**：
1. `sys_user` 增列 `must_change_password tinyint default 0`（加列不删列，符合演进铁律）；
2. `createUser` 接受随机初始口令或强制设置 `must_change_password=1`；
3. 登录成功后若标记为需改密，只允许访问改密接口，其余接口返回 428/403；
4. 增加口令复杂度校验（长度 ≥ 8、四类字符至少三类），拒绝弱口令字典。

**验证方式**：单测 —— 新建用户后用 `123456` 登录应被拒（或登录后强制跳改密）；改密后方可访问业务接口。

## 附录 B：授权覆盖扫描脚本（核心逻辑）

```python
import io, os, re
JAVA = r"src/backend/src/main/java"
MAPPING = re.compile(r'@(RequestMapping|GetMapping|PostMapping|PutMapping|DeleteMapping|PatchMapping)\s*\(')
PERM = re.compile(r'@RequirePerm\b')
PUBLIC = ('/auth/login', '/auth/logout', '/captcha')

for dp, _, fs in os.walk(JAVA):
    for fn in fs:
        if not fn.endswith('Controller.java'):
            continue
        src = io.open(os.path.join(dp, fn), encoding='utf-8', errors='replace').read()
        cls = re.search(r'\n(public\s+)?class\s+\w+', src)
        cls_pos = cls.start() if cls else len(src)
        class_perm = bool(PERM.search(src[:cls_pos].split('*/')[-1]))
        for m in MAPPING.finditer(src):
            if m.start() <= cls_pos:
                continue                      # 跳过类级 @RequestMapping（非端点，勿虚增分母）
            lo = max(src.rfind('}', 0, m.start()), src.rfind('{', 0, m.start()),
                     src.rfind(';', 0, m.start()))
            hi = src.find('{', m.end())
            unit = src[lo + 1: (hi if hi > 0 else m.end() + 400)]   # 注解块 + 方法签名
            has = bool(PERM.search(unit)) or class_perm
            if not has:
                summ = re.search(r'@Operation\(summary\s*=\s*"([^"]*)"', unit)
                print("%s:%-5d %-9s %s" % (fn, src.count('\n', 0, m.start()) + 1,
                      m.group(1).replace('Mapping', ''), summ.group(1) if summ else ''))
```
