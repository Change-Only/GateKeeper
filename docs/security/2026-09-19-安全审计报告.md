| 项目 | 说明 |
|---|---|
| 报告编号 | **T-SEC-1** |
| 审计日期 | 2026-09-19 |
| 审计对象 | GateKeeper（API 全生命周期管理平台 / APIM），后端 `src/backend`、前端 `src/frontend` |
| 审计基线 | 提交 `631819e`（T19 代码收口）+ `19476f8`（T19 文档） |

| 审计方法 | 自研注解覆盖扫描器（全量 31 个 Controller / 212 个方法级端点）× 人工取证复核 × 三维并行专项（密码学 / 请求伪造 / 认证会话）；**P0 结论已由独立复核轮重算** |
| 结论 | **存在 6 项 P0、9 项 P1、9 项 P2**。核心风险不在密码学与注入（这两块做得相当扎实），而在 **授权模型默认放行** 与 **密钥管理自检失效** |

---

## 0. 结论摘要

**一句话**：本系统"防护面"（签名、防重放、加密、注入防御）质量明显高于同类项目；但"授权面"是**默认允许** —— **212 个端点中 100 个（47%）后端无任何权限校验**，含 10 个写操作端点：最低权限账号即可关闭封禁、关闭告警、改写加密配置、无限延长授权；同时 `SecurityStartupCheck` 这道"最后防线"被自身配置默认值绕过。

| 严重级 | 数量 | 主题 |
|---|---|---|
| 🔴 P0 | 6 | 授权默认放行（根因）、延期授权绕过、安全防护可被注销、加密配置可被改写、主密钥明文入库、**调用报文可被任意账号全量读取导出** |
| 🟠 P1 | 9 | 密钥自检失效、网关 SSRF、会话与权限撤销不即时、通知渠道 SSRF、ECB 落库、登录锁定可被武器化、**口令散列泄漏**、**默认口令 123456**、**数据权限从未实现** |
| 🟡 P2 | 9 | 文档免认证暴露、陈旧依赖、内网地址入库、固定口令种子、错误回显、CORS 组合风险、短密钥掩码、**环境配置无掩码（内网拓扑暴露）**、**`@RequirePerm` 空值 fail-open** |

**风险优先级建议**：P0-1 是根因，应先收紧拦截器默认策略（改动小、收益最大），再逐个补齐 10 个写端点的注解。

## 1. 审计范围与信任边界

### 1.1 资产清单

| 层 | 组件 | 说明 |
|---|---|---|
| 入口 1 | `/api/gateway/**` | 网关代理，**不走 JWT**，用 AppKey + 签名鉴权（`WebConfig:46` 显式放行） |
| 入口 2 | `/api/**`（其余） | 管理后台，JWT 认证 + `@RequirePerm` 授权 |
| 入口 3 | `/doc.html`、`/v3/api-docs/**` | Knife4j 接口文档，**免 JWT 免授权**（`WebConfig:47-51`） |
| 数据 | MySQL `gatekeeper`（42 表）+ Redis | 主数据：接口资产 / 应用身份 / 授权关系 |
| 密钥 | `application.yml` 默认值 → `GATEKEEPER_*` 环境变量 | JWT 签名密钥、落库 KEK、DB 口令 |

### 1.2 关键架构事实（已核实，非推测）

1. **未引入 Spring Security**（`pom.xml` 无 `spring-boot-starter-security`），认证与授权全部自研。
2. 认证 = `config/JwtAuthInterceptor.java`（**只验令牌，不查数据库用户状态**）。
3. 授权 = `security/PermissionInterceptor.java`，**仅对带 `@RequirePerm` 的 handler 生效**，第 64-67 行对无注解者**直接放行**，注释写明「兼容存量」。
4. 设计口径（`docs/backend-补课-合同.md:33`）：仅**高危写操作**加 `@RequirePerm`，读操作与低危写操作**不强制**（页面可见性由菜单 perm 控制）；同文件 R5 预留审计接口：「若要求读也鉴权，需统一调整切面」。

> 故本报告对"读端点无注解"**不作为缺陷计数**（属既定策略），但在 §2.1 指出其在 10 个写端点上的**具体后果**，并说明"页面可见性"不构成访问控制。

## 2. 🔴 P0 发现

### P0-1 授权模型默认放行：47% 端点无后端权限校验，含 10 个写操作

**位置**：`security/PermissionInterceptor.java:64-67`（根因）；各 Controller（暴露点）

```java
RequirePerm requirePerm = methodAnnotation != null ? methodAnnotation : classAnnotation;
if (requirePerm == null) {
    // 无注解 → 不拦截（兼容存量）
    return true;
}
```

**全量比对结果**（脚本口径：仅统计方法级 mapping，已排除类级 `@RequestMapping`）。
下表为**独立复核轮重算后的修正值**（初版少计 8 个端点；09-24 第三轮严格复算再各修正 +6）：

| 指标 | 数值 |
|---|---|
| Controller 文件 | 31 |
| 方法级端点 | **212** |
| 受 `@RequirePerm` 保护 | **112（53%）** |
| **无任何权限注解** | **100（47%）** |
| └ 其中**写操作**（POST/PUT/DELETE） | **11**（含 `/auth/login`，实质 10 个） |

**两路交叉校验（09-24 严格口径）**：① 全量 mapping 注解行 **237**，类级 `@RequestMapping` **25** 个（⚠️ **不是 31**：31 是「含 mapping 注解的 Controller 文件数」，其中 `AppController` / `DashboardController` / `EncryptionConfigController` / `InterfaceController` / `InterfaceProtectionController` / `PermissionController` 6 个无类级前缀）⇒ **方法级端点 = 237 − 25 = 212**；② 全仓 `@RequirePerm` 注解行恰 **112**，与受保护端点**一一对应**、**孤立注解 0**（15 处注释字样已排除）；项目**无类级 `@RequirePerm`**（`PermissionInterceptor.java:61` 的 `getBeanType()` 读取能力无人使用）。

> ⚠️ **扫描陷阱**：`controller/AppController.java:94` 的 Javadoc 写了"刻意不加 `@RequirePerm`"，**子串扫描会误判为「受保护端点」**，必须按注解语法匹配（源码注释另有 15 处字样，不排除会让受保护端点数从 112 虚增到 115）。
>
> 🔧 **09-24 勘误**：本节此前写作 `237 − 31 = 206`，**减数用错**（31 是文件数而非类级注解数），端点总数与无注解数各**少计 6**；权威值见上表（212 / 112 / 100）。
>
> 📌 **统计口径声明**：`controller/GatewayController.java:54` 无注解且接受写动词，但属**数据面入口**（`GatewayCore` 做 AppKey + 签名鉴权），不计入管理面缺口；纯 HTTP 动词口径下"无注解写端点"会变成 12，本报告统一以**管理面**为准。

**10 个可被任意登录用户调用的写操作端点**：

| # | 方法 | 路径 | 文件:行 | 危害 |
|---|---|---|---|---|
| 1 | POST | `/grant/{id}/renew` | `grant/GrantController.java:90` | **绕过授权到期**（见 P0-2） |
| 2 | POST | `/permission/{id}/renew` | `controller/PermissionController.java:144` | 同上（同一操作的第二处暴露） |
| 3 | POST | `/block-rule/{id}/toggle` | `controller/BlockRuleController.java:93` | **关闭 IP 封禁** |
| 4 | PUT | `/block-rule/{id}/update` | `controller/BlockRuleController.java:81` | 篡改封禁阈值 |
| 5 | POST | `/alarm-rule/{id}/toggle` | `alarm/AlarmRuleController.java:106` | **关闭告警规则** |
| 6 | PUT | `/alarm-rule/{id}/update` | `alarm/AlarmRuleController.java:94` | 篡改告警阈值/静默告警 |
| 7 | POST | `/encryption/interface` | `controller/EncryptionConfigController.java:55` | **改写接口加解密配置（含 key）** |

**对比证据（同一文件内相邻方法的注解不一致，证明是遗漏而非设计）** —— `grant/GrantController.java`：

```java
@RequirePerm(value = "grant:create",  risk = true) @PostMapping("/create")   // ✅ 61-63
@RequirePerm(value = "grant:approve", risk = true) @PostMapping("/{id}/approve") // ✅ 68-70
@RequirePerm(value = "grant:reject",  risk = true) @PostMapping("/{id}/reject")  // ✅ 75-77
@RequirePerm(value = "grant:revoke",  risk = true) @PostMapping("/{id}/revoke")  // ✅ 82-84
@Operation(summary = "延期授权")                    @PostMapping("/{id}/renew")   // ❌ 89-90 无注解
```

**可利用性**：只需一个**任意权限的合法账号**（如只读账号），curl 直接打端点即可，**不经过前端页面**；前端"菜单可见性"不构成防护。

**修复方案**：

1. **立即** —— 把拦截器默认策略由"放行"改为"拒绝"，用白名单显式放行只读端点：

```java
// PermissionInterceptor.preHandle
if (requirePerm == null) {
    // 默认拒绝：仅放行显式登记为「公开只读」的端点
    String key = request.getMethod() + " " + request.getRequestURI().substring(contextPath.length());
    if (PUBLIC_READ_ENDPOINTS.contains(key)) {   // 集中维护的只读白名单
        return true;
    }
    log.warn("Blocked un-annotated endpoint: {} {}", request.getMethod(), request.getRequestURI());
    reject(response, 403, "该接口未登记访问策略，已拒绝");
    return false;
}
```

> ⚠️ **上面那段示例是方向示意，不要照抄**（09-24 实测）：把 100 个无注解端点里的 89 个只读端点全列入 `PUBLIC_READ_ENDPOINTS`，与「默认放行」**安全等价**（零收益，却新增「漏列即 403」回归风险）。**可行做法是按 HTTP 动词分治**：
>
> ```java
> // 可行版本：无注解时按 HTTP 动词判定
> if (requirePerm == null) {
>     if (WRITE_METHODS.contains(request.getMethod())
>             && !isPublicWriteEndpoint(request)) {   // 仅放行 POST /auth/login 等极少路径
>         reject(response, 403, "该写接口未登记访问策略，已拒绝");
>         return false;
>     }
>     return true;   // 只读仍放行（读侧收敛待后续单独完成）
> }
> ```

2. **然后（逐个补齐）** —— 为 §2.1 表格 10 个写端点补 `@RequirePerm`，复用同域既有码、不新增（示例）：
   - `POST /grant/{id}/renew`、`POST /permission/{id}/renew` → **`grant:approve`**（延期实质是"重新批准有效期"，与审批同风险级）
   - `POST /block-rule/{id}/toggle`、`PUT /block-rule/{id}/update` → 复用 `block_rule:update`
   - `POST /alarm-rule/{id}/toggle`、`PUT /alarm-rule/{id}/update` → **`alarm_rule:create`**（从"可关告警"看，风险等同创建）
   - `POST /encryption/*` → **`api:env:update`**
   - `PUT /alert/*/read` → `alert:read`（新增或复用）

3. **前端对齐** —— 同期补闸门，如 `views/perm/PermMatrix.vue:141` 的「续期」按钮当前仅 `v-if="row.status === 1"`，需加 `&& hasPerm('grant:approve')`。

**验证方式**：最低权限账号（如仅 `log:call:list`）curl 上述端点，改前应 200/成功、改后应 403；只读端点仍应为 200（防过度收紧）。

### P0-2 延期授权无权限 —— 直接绕过"授权到期"这一唯一时间防线

**位置**：`grant/GrantController.java:89-93`、`controller/PermissionController.java:143-148`

```java
@Operation(summary = "延期授权")
@PostMapping("/{id}/renew")
public Result<AppApiGrant> renew(@PathVariable Long id, @Valid @RequestBody GrantRenewRequest req) {
    return Result.success(grantService.renew(id, req.getValidTo()));   // validTo 由请求体完全控制
}
```

**影响**：授权模型是 Default Deny + 有效期控制（`app_api_grant.status=1` 且 `validFrom <= today <= validTo`，`GrantExpireJob` 每日 02:00 置过期）。`renew` 把 `validTo` 交给请求体任意指定 ⇒ **任何登录用户可将任意授权无限续期**，使到期机制、`GrantExpireJob`、网关双保险全部失效。

**放大条件**：`GET /grant/list`、`GET /grant/pending`、`GET /permission/pending` 同样无注解 ⇒ 可先枚举全部授权 ID 与到期日，再有选择地续期（**外部视角：可让已撤销之外的全部授权永久有效**）。

**修复方案**：同 P0-1 第 2 条（补 `grant:approve`），并在服务层加**业务约束**（不依赖单一权限点）：
- `validTo` 不得为空、不得早于当前 `validTo`（防"缩短后伪造"）、单次与累计延期上限（如单次 ≤365 天）；
- 延期必须写 `api_change_log` / 审计日志（当前 `renew` 未走 `@ApiChangeLog`）。

**验证方式**：单测 3 例（越权续期 403 / `validTo` 早于现值 400 / 超上限 400）；`PermMatrix` 页双身份差分确认按钮可见性。

### P0-3 安全防护可被静默注销（封禁规则 / 告警规则的启停与修改无权限）

**位置**：`BlockRuleController.java:81,93`、`AlarmRuleController.java:94,106`、`AlertController.java:77,89`

**影响链**：这是**完整入侵所需的最后一块拼图**。所有入侵痕迹都产出告警（5 类检测器 → `security_event` → 告警规则 → 通知渠道），拿到任意账号后即可：
1. `POST /block-rule/{id}/toggle` 关闭自动封禁 → 高频爆破不再被封；
2. `POST /alarm-rule/{id}/toggle` 关闭告警规则 → 不再产生通知；
3. `PUT /alert/read-all` 清空未读 → 运维失去感知。

三者叠加 = **在告警系统被"合法"静音的前提下持续攻击**。

**修复方案**：补注解（同 P0-1）+ 两条纵深防御：
- **启停强制审计**：`block_rule` / `alarm_rule` 的 toggle 走 `@ApiChangeLog` 或写 `sys_operation_log`（高危操作必须留痕、**不可被静默**）；
- **兜底告警**："封禁规则全停用"或"告警规则全停用"时由后台任务直接产生一条 `CRITICAL` 通知（不经规则引擎，防"关规则即无告警"自锁）。

**验证方式**：低权限账号调 toggle → 403；管理账号调 toggle → 成功且 `sys_operation_log` 新增一行。

### P0-4 平台加解密配置可被任意登录用户改写

**位置**：`controller/EncryptionConfigController.java:54-59、81-86`（**整个类 5 个端点全部无 `@RequirePerm`**）

```java
@Operation(summary = "保存接口加密配置")
@PostMapping("/interface")
public Result<Void> saveInterfaceConfig(@RequestBody ApiEncryptionConfig config) {
    apiEncryptionConfigService.saveConfig(config);   // 算法 / 密钥 / 开关 全部来自请求体
    return Result.success();
}
```

**影响**：请求体直接反序列化为配置实体并落库，**无参数校验、无归属校验、无权限校验**，攻击者可：
- 将模式置为 `DISABLED` ⇒ 请求体与响应**明文传输**（含敏感字段）；
- 写入**自己已知的密钥** ⇒ 中间人可解密并伪造报文。

**修复方案**：
1. 补 `@RequirePerm("api:env:update")`（与 `ApiEnvConfigController` 同域风险级）；
2. 服务层加**输入校验**：算法白名单（仅 AES-256-CBC / SM4）、拒绝空/过短密钥、拒绝请求体明文提交密钥（改为仅回显掩码）；
3. 该接口属历史遗留（新链路为 `ApiGroupEncryptionConfigController` / `InterfaceProtectionController`），若确认无前端调用建议**直接下线该 Controller**（符合"不保留无主入口"）。

**验证方式**：`grep -rn "encryption/interface" src/frontend/src` 确认引用；有引用则补权限后回归，无引用则删除并回归 773 用例。

### P0-5 落库主密钥（KEK）明文入库

**位置**：`docs/T17-契约记录.md:50`（**已被 git 跟踪**）

```
- 密钥：复用落库 KEK `gatekeeper.crypto.aes-key`（`application.yml` 默认
  `<已脱敏:41位AES-KEK>`），经 `CryptoKeyUtil.toBase64Key` 规范化为 32 字节。
```

**取证（用 `git grep` 只搜被跟踪文件，排除"仅本地存在"的误判）**：

| 密钥 | 在被跟踪文件中命中 |
|---|---|
| `<已脱敏:41位AES-KEK>`（AES KEK） | **✅ 1 个文件：`docs/T17-契约记录.md:50`** |
| JWT 签名密钥（49 位） | 0 |
| DB 口令（22 位） | 0 |

**旁证**：`.gitignore:41` 已排除 `application.yml`（注释：主配置含真实密钥，永不入库）—— 项目**已意识到**该问题并处理了配置，但**文档里同一把密钥漏了**。

**泄漏面收窄（独立复核轮）**：`application.example.yml`（被跟踪）**不含**该密钥值、`application.yml` 自身未被跟踪 ⇒ 泄漏**仅限 `docs/T17-契约记录.md:50` 一处一行**。这降低紧迫度但**不改变结论**：该值已随 git 历史分发，仍须轮换。

**影响**：这把 KEK 是**全库密文的唯一钥匙**——`app_secret`、接口路径/参数（T17）、通知渠道密码（T09）均用它（或同源）加密。拿到仓库即拿到钥匙 ⇒ 若再拿到数据库备份/只读账号，全部密文即刻还原。

**修复方案（按序三步）**：
1. **换密钥（唯一彻底的做法）**：`GATEKEEPER_AES_KEY` 轮换为新随机密钥（`openssl rand -base64 32`），并**用一次性迁移脚本重加密全库密文**（`app_secret` / `app_credential.*` / `notify_channel.channel_config` / T17 相关列）。⚠️ 依赖尚未实现的 R8 轮换能力（T09），需先补齐双密钥读取（旧解密 → 新加密）。
2. **清文档**：把 `docs/T17-契约记录.md:50` 的原文改为占位符（`<见 .env>`）；全仓扫同类文档（`git grep -nE "aes-key|aesKey|GATEKEEPER_AES_KEY"` + 高熵串扫描 —— **不要用密钥前缀做检索词**，那本身就是再次复现原文）。
3. **防回归**：在 pre-commit 钩子中加入密钥形态扫描（高熵 32+ 位字符串 + 常见前缀），阻断再次入库。

> 🔴 **历史维度残留（09-24 实测 · 必须补做）**：从**当前版本**删掉明文**不等于**从仓库中消除 —— 实测该值出现在 **10 个提交**中（`2b2be00` 引入、直到 `45d0941` 仍含，仅 `fae8bee` 才从工作树删除），`git show 2b2be00:docs/T17-契约记录.md` 即可读出原文。因此：

### P1-2 网关转发 SSRF：目标地址无白名单、无内网/元数据拦截

**位置**：`gateway/handler/ForwardHandler.java:124,145-150`

```java

...
```

**核实结果**：全仓**未发现**主机白名单或私网地址（`127.` / `10.` / `172.16-31` / `192.168.` / `169.254.169.254`）拦截逻辑；`HttpClientConfig` 与 `ForwardHandler` **均未显式设置重定向策略**（`setRedirectStrategy` 命中 **0**），故使用 HttpClient 默认策略（跟随 301/302/307）。

**影响**：
- **写权限者 → 内网探测**：有 `api:update` / `api_env_config:*` 写权限者（见 P0-1）可把 `backend_url` 指向内网任意地址，借网关做**内网端口扫描与服务探测**（响应体原样返回给调用方）；
- **云环境升级为凭证窃取**：公有云下 `http://169.254.169.254/latest/meta-data/iam/security-credentials/` 可经网关取回**实例角色临时凭证** ⇒ 接管云账号，**此时应升级为最高优先级**；
- **重定向绕过**：即便加了朴素主机白名单，跟随重定向仍可跳到非白名单地址。

**修复方案**：
1. 转发前统一做**目标地址校验**（新建 `UpstreamAddressGuard`）：
   - **解析后校验** IP 是否属私网/回环/链路本地/组播/保留段（含 IPv6 `::1`、`fc00::/7`、`fe80::/10`），非校验字符串（防 DNS rebinding 与十进制 IP 绕过）；
   - 云元数据地址（`169.254.169.254`、`metadata.google.internal`）**硬拒绝**；
   - 需访问内网的场景改**显式白名单**（`api_env_config` 增"允许的主机后缀"，或配置项 `gatekeeper.gateway.allowed-hosts`），默认空 = 只允许公网。
2. **关闭自动重定向**：`HttpClientConfig` 显式 `setRedirectStrategy(new LazyRedirectStrategy())` 或禁用；如需跟随则每跳重复第 1 步。
3. 同类面一并加固（见 P1-4）。

**验证方式**：单测覆盖 8 类地址（`127.0.0.1`、`10.0.0.1`、`192.168.1.1`、`172.20.0.1`、`169.254.169.254`、`[::1]`、十进制 `2130706433`、解析后私网的域名）→ 全部拒绝；公网 → 放行。

### P1-3 会话与权限撤销不即时（最长 120 分钟的"僵尸会话" + 24 小时权限滞留）

**涉及三处，可叠加**：

1. **`/auth/logout` 不实现吊销** —— `AuthController.java:37` 注释明示「前端清除令牌即可」。JWT 无服务端状态，登出后**令牌仍然有效直至 `exp`**。
2. **认证拦截器不查用户状态** —— `JwtAuthInterceptor.java:46-55` 只解析令牌取 `uid`，**不校验用户是否已停用/删除**，故 `PUT /system/user/{id}/status/0` 与 `DELETE /system/user/{id}` **对已登录会话无任何效果**。
3. **权限缓存 TTL 24 小时** —— `PermissionCacheService.java:56`（`CACHE_TTL_HOURS = 24`），`PermissionInterceptor` 每次请求只读该缓存。

**量化**：`gatekeeper.jwt.expire-minutes: 120`（`application.yml:106`，已被 `JwtUtil:25` 读取）⇒ **停用/降权一个用户后，其令牌最长再有效 120 分钟，权限最长滞留 24 小时**。

> 附带发现：运维纪律「改完权限种子必须 `DEL gk:perm:*`」是本问题的**人工补偿**。代码里的 `replaceUserRoles`（"给用户分配角色"）**没有任何 Controller 调用**（`SysUserServiceImpl.updateUser` 也不处理角色）⇒ "用户-角色分配"未接线、只能改库。

**修复方案**：
1. **缩短有效窗口**：`gk:perm` TTL 从 24h 降到 5-10 分钟（权限点小、回源廉价）；`PermissionCacheService` 已实现"未命中回源"，无功能风险。
2. **令牌吊销**：引入 Redis 黑名单（`gk:jwt:revoked:{jti}`，TTL = 剩余有效期），`/auth/logout` 写入、`JwtAuthInterceptor` 校验。
3. **登录态校验用户状态**：`JwtAuthInterceptor` 按 `uid` 读用户（可复用 5-10 分钟短缓存），状态非 1 或已删除 ⇒ 401。
4. **停用/删除时主动失效**：`SysUserServiceImpl.updateStatus` / `deleteUser` 调 `permissionCacheService.invalidateUser(id)` + 写吊销标记（服务已具备能力，缺的只是调用）。
5. **接线"用户-角色分配"**：让 `updateUser` 调用现成的 `replaceUserRoles`（含 afterCommit 失效），或在 `SystemController` 增加端点。

**验证方式**：E2E —— 用户 A 登录 → 管理员改 A 角色 → A 的旧令牌访问新权限端点应 403；停用 A 后 A 的令牌应立即 401（而非等 2 小时）。

### P1-5 落库加密使用 AES/ECB（确定性密文、无完整性保护）

**位置**：`app_secret`、通知渠道密码的落库加解密；T19 已把 `sys_config['secret.encrypt.algo']` 更正为 `AES/ECB/PKCS5Padding`，即**确定了 ECB 就是现实**。

**影响**：
- **无 IV ⇒ 确定性**：相同明文永远产生相同密文；拿到库（或只读账号）即可对 `app_secret` 等做**等值比对/字典攻击**（低熵密钥可被批量还原），并观测"哪些应用共用同一密钥"；

**对照**：T17 的新链路（`InterfaceCryptoService`）做得**很好** —— `enc:v1:<iv>:<cipher>`、**每次随机 16 字节 IV**、CBC。问题只在**老的落库链路**。

**修复方案**：
1. 统一改 `AES-256-CBC` + 随机 IV（复用 T17 已验证的 `CryptoKeyUtil` 与格式），密文加版本前缀（如 `enc:v2:`），**读路径双格式兼容**（存量 `enc:` 与无前缀明文照旧可读）；
2. 迁移脚本一次性重加密（与 P0-5 的 KEK 轮换**合并到同一维护窗口**，避免两次全库重写）；
3. 长期引入 AEAD（`AES-GCM`）获得完整性保护。

**验证方式**：同一明文加密两次密文不同；旧格式数据仍可解密；`mvn -o test` 全绿。

### P1-6 登录锁定可被武器化（账号锁定 DoS），且无验证码

**位置**：`controller/AuthController.java:79-87,138-151`

**核实结果**：全仓**无验证码**实现（关键词 `captcha`/`Captcha`/`验证码` 命中 0）；无按 IP/全局的登录限速。

**影响**：
- **账号锁定 DoS**：对管理员用户名**故意失败 5 次**即可锁定其 10 分钟，循环即可让**所有管理员无法登录**（而处置攻击正需管理员登录）；

2. 密码喷洒缓解：加**全局登录速率限制**（如 100 次/分钟）与失败响应**固定延迟**（如 300ms）；
3. 管理后台登录加**验证码**（连续失败 3 次后出现）；
4. Redis 异常不要 500：`get/increment` 包 try/catch，降级为"仍允许登录但记 ERROR"（避免 Redis 抖动导致管理后台整体不可登录）。

**验证方式**：5 次错误密码后，**另一 IP** 用正确密码应能登录；不存在的用户名不应产生 `login_fail:*` 键。

**影响**：新建账号初始口令恒为 `123456`，且代码**显式忽略**请求体传入的口令；系统**无"首次登录强制改密"**。配合 P1-7 的散列泄漏与 P1-6，形成完整攻击链：**读散列 → 确认是 `123456` → 直接登录**。

**修复方案**：
1. `sys_user` 增列 `must_change_password tinyint default 0`（加列不删列）；
2. `createUser` 用随机初始口令或强制 `must_change_password=1`；
3. 登录后若需改密则只允许访问改密接口，其余返回 428/403；
4. 加口令复杂度校验（长度 ≥ 8、四类字符至少三类），拒弱口令字典。

**验证方式**：新建用户后用 `123456` 登录应被拒（或强制跳改密）；改密后方可访问业务接口。

### P1-9 数据权限从未实现：`role_data_scope` 配置是空转

**位置**：`config/MybatisPlusConfig.java:22-25`

```java
public MybatisPlusInterceptor mybatisPlusInterceptor() {
    MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
    interceptor.addInnerInterceptor(new PaginationInnerInterceptor(DbType.MYSQL));
    return interceptor;      // ← 仅注册了分页插件
}
```

**取证**：全仓检索 `DataPermissionInterceptor` **命中 0**；但系统提供了完整的配置界面与存储：`controller/DataScopeController.java`（`/role-data-scope/*`）、`service/impl/RoleDataScopeServiceImpl.java`、`sys_role_data_scope` 表。

**影响**：`sys_role_data_scope` 配的范围**完全不生效** —— 任何登录用户在任一"列表"端点看到的都是**全量数据**（全应用/接口/日志/审计），是 P0-1 的危害放大器：期望只读账号只见自己范围，实际可见全部。**界面让人以为配了隔离，实际没有** —— 比"没有该功能"更危险。

**修复方案**（推荐第 1 条）：
1. **显式落地范围过滤**：在核心列表 Service（`ApiInterface` / `ApiCallLog` / `AppApiGrant` / 审计）注入当前用户可管理的 `app_id` / `biz` 范围并拼进 `QueryWrapper`；范围来源 `sys_role_data_scope` + `sys_user_role`。
2. **接入 `DataPermissionInterceptor`**：MyBatis-Plus 官方插件 + 自定义 `DataPermissionHandler`，**但必须严格限定生效表白名单**，否则会给全站 SQL 追加条件、引发大面积回归。

> 无论选哪条，都建议**先决定 `sys_role_data_scope` 的语义**：短期不实现就应在界面停用该页，避免"配了不生效"的误导（与 T19"配置脱钩"同类）；**同族**：`sys_config` 中 13 项「未接线（预留）」配置亦属同类隐患。

**验证方式**：以"范围只有 A 应用"的账号登录，调 `/api/interface/list`、`/api/log/list` 应只见 A 应用的记录；用超管账号应见全量。
