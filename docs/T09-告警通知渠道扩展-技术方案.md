## 2. 目标渠道与字段需求

### 2.1 范围裁定（基于 §1.4 现状的修正认知）

lead 派工原文「邮件（SMTP）+ 企业微信群机器人 webhook 两种」。**实测修正**：企微 webhook **后端真发已存在**（§1.4），故本方案实际工作量 = ①EMAIL 由桩发改为 SMTP 真发；②企微/钉钉 webhook 发送增强（errcode 判定）；③打通前端配置链路（缺陷①③）。**不做** SMS（路线图未排、无需求方）。

### 2.2 channel_config JSON Schema（冻结契约 v1）

按渠道类型定义（存 `notify_channel.channel_config`，varchar(1024) 内）：

```jsonc
// WECOM / DINGTALK（现状字段名保持兼容，NotifySender:103 已读 webhook/url）
{ "webhook": "https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=xxx" }

// EMAIL（本方案新增）
{
  "smtpHost": "smtp.example.com",
  "smtpPort": 465,
  "ssl": true,                        // 465=true, 25/587=false（587 走 STARTTLS 自动协商）
  "username": "alert@example.com",
  "password": "enc:BASE64密文",        // ⚠️ 唯一加密字段，见 §3.3；enc: 前缀标记密文
  "from": "alert@example.com",
  "to": "ops-a@example.com,ops-b@example.com"   // 逗号分隔收件人
}
```

长度实测估算：加密后 password（Base64 膨胀 ~1.4×）+ 其余明文字段 ≈ 250–400 字符，**1024 上限充足，无需 DDL**。**裁定：本轮零 DDL**（18 表只加列不加废的最小化实践——连列都不加）。

## 3. 后端设计

### 3.1 发送适配器（组件式策略，对齐 Detector 风格）

新增包 `com.gatekeeper.alarm.sender`：

```java
/** 渠道发送适配器 SPI —— 每类型一个 @Component 实现，对齐 security/*Detector 组件式策略风格 */
public interface ChannelSender {
    String[] supportTypes();                    // 如 {"WECOM","DINGTALK"} / {"EMAIL"}
    boolean send(NotifyChannel channel, String title, String content);  // 永不抛异常，返回是否成功
}

@Component public class WebhookSender implements ChannelSender { ... }   // WECOM+DINGTALK：迁自 NotifySender.sendWebhook，新增 errcode 判定（见 R5）
@Component public class EmailSmtpSender implements ChannelSender { ... } // 新增：SMTP 真发
```

`NotifySender` 保留类名与 `send(channel,title,content)` 签名（**调用方 AlarmRuleServiceImpl/NotifyChannelServiceImpl 两处零改动**），内部改为：注入 `List<ChannelSender>` 按 type 路由；**无匹配实现时退化为现状桩发 log（不破坏 SMS/WEBHOOK 存量行为）**。`RestTemplate` mock 注入构造器保留（`NotifySenderTest` 既有范式不破坏）。

### 3.2 EmailSmtpSender 设计（pom 加 1 依赖）

- 依赖：`org.springframework.boot:spring-boot-starter-mail`（Boot 2.7 + Java 8 ⇒ javax.mail 系，与现有 starter 族一致）。**不用**全局 `spring.mail.*` 配置（每渠道 SMTP 各异，配置在 channel_config），按渠道动态构造 `JavaMailSenderImpl`（可按 host:port:user 缓存实例，防每次发送重建）。
- 发送：HTML/文本邮件，title 为主题、content 为正文；收件人按 `to` 逗号拆分；任何异常 catch → false（对齐「绝不抛给调用方」铁律）。
- 超时：`mail.smtp.connectiontimeout/readtimeout` 设 5s/10s（对齐网关 default-timeout 量级），防 SMTP 黑洞拖垮 10s 周期的评估线程。

### 3.3 配置加密存储（复用既有 AES，FAIL-CLOSED）

- **写路径**（create/update，`NotifyChannelServiceImpl` 内新增私有方法，照抄 `encryptSecret` 范式）：解析 channelConfig JSON → 仅对 `password` 字段加密 → 密文带 `enc:` 前缀回填 → 落库。**加密失败抛 GatewayException，拒绝落库**（FAIL-CLOSED，对齐 `AppCredentialServiceImpl:392-395`）。
- **读路径**（发送时）：`enc:` 前缀 → 解密后用；无前缀（明文历史数据）→ 直接用并 log warn（**演进式兼容**，不强制清洗存量）。
- **传输脱敏**（list/detail 返回前）：password 字段替换为 `toSecretMask` 掩码（首4+****+末4）。编辑保存时前端回传掩码原文 ⇒ 后端识别「等于掩码格式且以 `****` 居中」则跳过该字段更新（防止掩码回写覆盖真密文）。
- 密钥：与 app_secret **共用** `gatekeeper.crypto.aes-key`（KEK 单一来源）。约束留档：**该密钥一旦轮换，channel_config 与 app_secret 须同批重加密**（风险 R8）。

### 3.4 幂等迁移 SQL

**本轮零 DDL、零新种子**。唯一 SQL 为可选的数据卫生（**不阻塞施工**，落 `docs/sql/t09-notify-hygiene.sql`，幂等）：

```sql
-- 可选：把存量 4 行失真的 last_test_result 置空，避免误导（配置全 NULL，历史"发送成功"系桩发时期回写）
UPDATE notify_channel SET last_test_result = NULL WHERE channel_config IS NULL AND last_test_result = '发送成功';
```

> `docs/sql/` 是**文档库 SQL 目录**（历史各批种子所在），执行仍由 lead 统一收口；本方案不执行。

## 4. 前端设计（不新增页面，只改 SysNotify.vue）

1. **动态表单重构**（修缺陷①③）：`#extra` slot 按 channelType 渲染：
   - WECOM/DINGTALK：`webhook`（完整 webhook URL 输入框，替换现 `botKey`——后端只认 `webhook`/`url` 字段，`botKey` 是**从未生效的伪字段**）；
   - EMAIL：`smtpHost`/`smtpPort`/`ssl`(switch)/`username`/`password`(show-password)/`from`/`to`，含必填校验（smtpHost/from/to 非空）；
   - 提交前**组装**：把这些散字段序列化为 channelConfig JSON 字符串随 form 提交（后端 `NotifyChannel.channelConfig` 同名属性会被 copyProperties 正确拷贝——缺陷①根因修复）。
2. **编辑回显**：`onEdit` 时解析 `row.channelConfig` JSON 反填散字段；password 显示后端掩码。
3. **类型切换**：channelType 变更时清空动态字段（防 SMTP 残留进 webhook 渠道）。
4. **修缺陷②**：移除 `remark` 列（表无此列）。
5. enum.js 的 channelType 4 值**不动**（SMS 不做，见 §2.1）。
