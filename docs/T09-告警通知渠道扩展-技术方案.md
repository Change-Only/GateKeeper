## 1. 现状盘点（全部实测，来源逐一标注）

### 1.1 表结构（DB 实查 `SHOW CREATE TABLE notify_channel` @ <MYSQL_HOST>:13306）

| 列 | 类型 | 说明 |
|---|---|---|

| `channel_type` | varchar(32) NOT NULL | 注释枚举 WECOM/DINGTALK/EMAIL/SMS/WEBHOOK，**无 CHECK 约束、无字典表绑定** |

### 1.2 存量数据（DB 实查）

| id | channel_name | type | status | channel_config | last_test_result |
|---|---|---|---|---|---|
| 1 | 交易研发-企微机器人 | WECOM | 1 | **NULL** | 发送成功 |
| 2 | 支付研发-钉钉机器人 | DINGTALK | 1 | **NULL** | 发送成功 |
| 3 | 平台告警邮件 | EMAIL | 1 | **NULL** | 发送成功 |
| 4 | 安全事件 Webhook | WEBHOOK | 0 | **NULL** | 连接超时，请检查配置 |

> ⚠️ **关键事实：4 行 `channel_config` 全部为 NULL。** 即存量 WECOM/DINGTALK 渠道虽后端代码支持真发，但**实际不可发**（`NotifySender.sendWebhook` 对 NULL config 返回 false）。「发送成功」的 last_test_result 是 EMAIL 桩发（恒 true，见 §1.4）时期回写的**历史失真数据**。

### 1.3 发送链路（读源码实测）

```
AlarmEvaluateJob（job/AlarmEvaluateJob.java:36 每 10s 实时 / :48 每 5min 离线，fail-open）
  → AlarmRuleServiceImpl.evaluateRealtime/evaluateOffline（:212/:224）
    → evaluateRule（:242）：阈值判定 → Redis 静默键 →
        ① AlertService.publish 落库告警（:270，失败不阻断）
        ② notifyChannelService.listByIds(rule.getChannelIds()) → NotifySender.send(ch,title,content)（:280，逐渠道 try/catch）
        ③ 写静默键（:288）
测试入口 ×2：
  - AlarmRuleServiceImpl.test(id)（:182-205）→ 同上发送
  - NotifyChannelServiceImpl.test(id)（:134-155）→ send 后回写 lastTestTime/lastTestResult("SUCCESS"/"FAILED")
```

`alarm_rule.channel_ids` 为**逗号分隔字符串、无外键**（`NotifyChannelServiceImpl.delete:121-128` 据此做引用完整性检查：被引用拒绝删除）。

### 1.4 发送能力矩阵（`alarm/NotifySender.java` 实测）

| channel_type | 现状 | 证据 |
|---|---|---|
| WECOM / DINGTALK | **真实发送**：解析 config JSON 的 `webhook`/`url` 字段 → RestTemplate POST text 消息 | `:77-79 → sendWebhook(:97-119)` |
| EMAIL | **桩发**：仅 log「would send via SMTP」，恒返回 true | `sendEmail(:124-130)` |
| SMS / WEBHOOK / 其他 | **桩发**：log 意图，恒返回 true | `:83-86` |
| 停用渠道（status=0） | sendWebhook 内跳过发送但**返回 true** | `:108-111`（语义缺陷，见风险 R4） |

异常语义：所有路径包 try/catch，**绝不抛给调用方**；webhook HTTP 非 2xx 时 `postForObject` 抛 `RestClientException` → 外层 catch → false。**但企微返回 HTTP 200 + body `{"errcode":非0}` 不会判失败**（风险 R5）。

### 1.5 前端现状（`src/frontend/src/views/system/SysNotify.vue` 实测）

- 类型枚举：`utils/enum.js:222-227` 硬编码 4 值（WECOM/DINGTALK/EMAIL/WEBHOOK），**无 SMS**；已有按类型分叉的动态表单（CrudDialog `#extra` slot，`:75-85`）：WEBHOOK→`webhookUrl`、EMAIL→`emailAddress`、WECOM/DINGTALK→`botKey`（show-password）。
- **缺陷①（P0）**：表单把 `webhookUrl`/`emailAddress`/`botKey` 作**顶层平铺字段**随 form 直接提交（`:178-192`），后端 `NotifyChannel` 无同名属性 ⇒ `BeanUtils.copyProperties`（`NotifyChannelServiceImpl.create:72`）**静默丢弃** ⇒ **channelConfig 永不写入**（「配置存不进去」根因，与 §1.2 全 NULL 互证）。
- **缺陷②（P3）**：表格 columns 渲染 `remark` 列（`:119`），但表无该列，恒显示空。
- **缺陷③（P3）**：编辑回显直接 `{...row}`（`:173`），未从 channelConfig 反解析动态字段（叠加缺陷①，编辑配置整体不可用）。
- API 层完整（`api/modules.js:560-578`：list/detail/create/update/delete/test 六函数），**无需改动**。

### 1.6 权限现状（`alarm/NotifyChannelController.java` 实测）

6 端点全部就位：list/detail 无注解；create=`notify_channel:create`(risk=true)、update=`sys:notify:update`(risk=true)、delete=`notify_channel:delete`(risk=true)、test=`notify_channel:test`(risk=true)。**本方案零新增端点、零新增码**，权限面不变。

### 1.7 依赖与加解密现状

- `pom.xml` **无任何 mail 依赖**（无 spring-boot-starter-mail / javax.mail / jakarta.mail；grep artifactId 实测）。已有：httpclient、hutool-all（含 bcprov）。
- 现成 AES 范式（**直接复用，勿另造**）：`AppCredentialServiceImpl.encryptSecret(:388-397)` —— `@Value("${gatekeeper.crypto.aes-key}")`（`:61`）注入 → `CryptoKeyUtil.toBase64Key()`（补齐 32 字节 AES-256）→ `cryptoService.encrypt("AES", plain, key, null, "ECB", "PKCS5Padding")`，**FAIL-CLOSED**（加密失败抛业务异常，绝不明文落库）。掩码范式 `toSecretMask(:402-407)`：首 4 + `****` + 末 4。
- 密钥来源：`application.yml:72` `gatekeeper.crypto.aes-key`（环境变量 `GATEKEEPER_AES_KEY` 可覆盖，`SecurityStartupCheck:66` 强校验 ≥32 位）。

### 1.8 策略模式风格基线（lead 要求对齐）

`com.gatekeeper.security` 包 5 个 Detector（HighFrequency/OffHours/AbnormalParam/AuthFail/PermissionBreach）为**组件式策略**：独立 `@Component` 类、构造注入依赖、`@Value` 配置、公共入口方法、整体 try/catch fail-open。**本方案的渠道适配器沿用此风格**（见 §3.1），不引教条 GoF 接口继承树。

## 2. 目标渠道与字段需求

### 2.1 范围裁定（基于 §1.4 现状的修正认知）

lead 派工原文「邮件（SMTP）+ 企业微信群机器人 webhook 两种」。**实测修正**：企微 webhook **后端真发已存在**（§1.4），故本方案实际工作量 = ①EMAIL 由桩发改为 SMTP 真发；②企微/钉钉 webhook 发送增强（errcode 判定）；③打通前端配置链路（缺陷①③）。**不做** SMS（路线图未排、无需求方）。

### 2.2 channel_config JSON Schema（冻结契约 v1）

按渠道类型定义（存 `notify_channel.channel_config`，varchar(1024) 内）：

```jsonc
// WECOM / DINGTALK（现状字段名保持兼容，NotifySender:103 已读 webhook/url）
{ "webhook": "https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=xxx" }

// EMAIL（本方案新增）
{
  "smtpHost": "smtp.example.com",
  "smtpPort": 465,
  "ssl": true,                        // 465=true, 25/587=false（587 走 STARTTLS 自动协商）
  "username": "alert@example.com",
  "password": "enc:BASE64密文",        // ⚠️ 唯一加密字段，见 §3.3；enc: 前缀标记密文
  "from": "alert@example.com",
  "to": "ops-a@example.com,ops-b@example.com"   // 逗号分隔收件人
}
```

长度实测估算：加密后 password（Base64 膨胀 ~1.4×）+ 其余明文字段 ≈ 250–400 字符，**1024 上限充足，无需 DDL**。**裁定：本轮零 DDL**（18 表只加列不加废的最小化实践——连列都不加）。

## 3. 后端设计

### 3.1 发送适配器（组件式策略，对齐 Detector 风格）

新增包 `com.gatekeeper.alarm.sender`：

```java
/** 渠道发送适配器 SPI —— 每类型一个 @Component 实现，对齐 security/*Detector 组件式策略风格 */
public interface ChannelSender {
    String[] supportTypes();                    // 如 {"WECOM","DINGTALK"} / {"EMAIL"}
    boolean send(NotifyChannel channel, String title, String content);  // 永不抛异常，返回是否成功
}

@Component public class WebhookSender implements ChannelSender { ... }   // WECOM+DINGTALK：迁自 NotifySender.sendWebhook，新增 errcode 判定（见 R5）
@Component public class EmailSmtpSender implements ChannelSender { ... } // 新增：SMTP 真发
```

`NotifySender` 保留类名与 `send(channel,title,content)` 签名（**调用方 AlarmRuleServiceImpl/NotifyChannelServiceImpl 两处零改动**），内部改为：注入 `List<ChannelSender>` 按 type 路由；**无匹配实现时退化为现状桩发 log（不破坏 SMS/WEBHOOK 存量行为）**。`RestTemplate` mock 注入构造器保留（`NotifySenderTest` 既有范式不破坏）。

### 3.2 EmailSmtpSender 设计（pom 加 1 依赖）

- 依赖：`org.springframework.boot:spring-boot-starter-mail`（Boot 2.7 + Java 8 ⇒ javax.mail 系，与现有 starter 族一致）。**不用**全局 `spring.mail.*` 配置（每渠道 SMTP 各异，配置在 channel_config），按渠道动态构造 `JavaMailSenderImpl`（可按 host:port:user 缓存实例，防每次发送重建）。
- 发送：HTML/文本邮件，title 为主题、content 为正文；收件人按 `to` 逗号拆分；任何异常 catch → false（对齐「绝不抛给调用方」铁律）。
- 超时：`mail.smtp.connectiontimeout/readtimeout` 设 5s/10s（对齐网关 default-timeout 量级），防 SMTP 黑洞拖垮 10s 周期的评估线程。

### 3.3 配置加密存储（复用既有 AES，FAIL-CLOSED）

- **写路径**（create/update，`NotifyChannelServiceImpl` 内新增私有方法，照抄 `encryptSecret` 范式）：解析 channelConfig JSON → 仅对 `password` 字段加密 → 密文带 `enc:` 前缀回填 → 落库。**加密失败抛 GatewayException，拒绝落库**（FAIL-CLOSED，对齐 `AppCredentialServiceImpl:392-395`）。
- **读路径**（发送时）：`enc:` 前缀 → 解密后用；无前缀（明文历史数据）→ 直接用并 log warn（**演进式兼容**，不强制清洗存量）。
- **传输脱敏**（list/detail 返回前）：password 字段替换为 `toSecretMask` 掩码（首4+****+末4）。编辑保存时前端回传掩码原文 ⇒ 后端识别「等于掩码格式且以 `****` 居中」则跳过该字段更新（防止掩码回写覆盖真密文）。
- 密钥：与 app_secret **共用** `gatekeeper.crypto.aes-key`（KEK 单一来源）。约束留档：**该密钥一旦轮换，channel_config 与 app_secret 须同批重加密**（风险 R8）。

### 3.4 幂等迁移 SQL

**本轮零 DDL、零新种子**。唯一 SQL 为可选的数据卫生（**不阻塞施工**，落 `docs/sql/t09-notify-hygiene.sql`，幂等）：

```sql
-- 可选：把存量 4 行失真的 last_test_result 置空，避免误导（配置全 NULL，历史"发送成功"系桩发时期回写）
UPDATE notify_channel SET last_test_result = NULL WHERE channel_config IS NULL AND last_test_result = '发送成功';
```

> `docs/sql/` 是**文档库 SQL 目录**（历史各批种子所在），执行仍由 lead 统一收口；本方案不执行。

## 4. 前端设计（不新增页面，只改 SysNotify.vue）

1. **动态表单重构**（修缺陷①③）：`#extra` slot 按 channelType 渲染：
   - WECOM/DINGTALK：`webhook`（完整 webhook URL 输入框，替换现 `botKey`——后端只认 `webhook`/`url` 字段，`botKey` 是**从未生效的伪字段**）；
   - EMAIL：`smtpHost`/`smtpPort`/`ssl`(switch)/`username`/`password`(show-password)/`from`/`to`，含必填校验（smtpHost/from/to 非空）；

2. **编辑回显**：`onEdit` 时解析 `row.channelConfig` JSON 反填散字段；password 显示后端掩码。
3. **类型切换**：channelType 变更时清空动态字段（防 SMTP 残留进 webhook 渠道）。
4. **修缺陷②**：移除 `remark` 列（表无此列）。
5. enum.js 的 channelType 4 值**不动**（SMS 不做，见 §2.1）。

## 7. 验收判据

1. **回归基线**：`mvn -o test` 全绿（378 基线 + 本轮新增，0 失败 0 错误）。
2. **能失败用例全数落地**（§5 T1–T8），其中 **T3 在施工前必红、施工后必绿**（语义缺陷修复的正面证明）。
3. **零 DDL / 零新码 / 零新 Controller**：红线校验（18 表结构无变化、@RequirePerm 集合不变、越界 0）。
4. **端到端（有外联环境）**：
   - EMAIL：界面对真实 SMTP 渠道点「测试」→ 收件箱收到标题「[测试通知] ×××」邮件 → lastTestResult=SUCCESS；
   - WECOM：真实群机器人 webhook → 群内收到消息 + errcode=0。
5. **降级验证（无外联环境，本机/内网）**：
   - EMAIL：本地起 mock SMTP（`python -m smtpd -c DebuggingServer -n localhost:1025` 或容器内 MailHog）→ smtpHost=localhost:1025 → 测试通过且 mock 端收到邮件原文；
   - WECOM：本地 mock HTTP（`python -m http.server` 返回 200 空 body）→ 发送判定走 errcode 解析路径；
   - 两项都不可用时：**以 T2/T3 mock 单测为验收依据**（方法纪律承 T07/T08：能失败的用例优先于「接口 200」）。
6. **安全断言**：DB 直查 `notify_channel.channel_config` 不含 SMTP 明文密码（`enc:` 前缀）；list 接口响应不含明文与密文（仅掩码）。
