> **问题**：T05 进入 Phase 4 后，全量权限链路核查发现**跨 Phase 的 P0 契约断裂**——前端 `menu.js` / `router/index.js` / `PermButton` 引用的部分 `perm_code` 从未写入 `sys_menu`，导致菜单永久不可见、接口调用必 403。
>
> **本文件**：给出权威侧裁决 + 完整对照表 + 新权限点清单 + 前端改动精确行号 + 角色授权矩阵 + 验证判据。
> **配套脚本**：`docs/sql/seed-perm-alignment.sql`（幂等，可重复执行）。
>
> **硬约束遵守**：不改任何 Java 源码；不改任何前端源码（仅文档标注改哪行）；不落库；不提交 git。

## 0. 权限数据链路（事实基础）

- 登录链路：`AuthController.login` → `PermissionCacheService.getUserPerms(uid)` → Redis `gk:perm:{uid}`；未命中回源 `loadPermsFromDb(uid)`：
  `sys_user_role`(user_id) → `sys_role_menu`(role_id) → `sys_menu`(type=3 AND status=1 AND perm_code IS NOT NULL)。
- **服务端无超管通配**（`'*'` 只在前端 `utils/perm.js`）。⇒ **任何未写入 `sys_menu` 的 perm_code，任何角色（含 SUPER_ADMIN）都永远拿不到。**
- 实测：admin(uid=1, roles=SUPER_ADMIN+ADMIN) permCount=42（= 全部已播种点）。
- 现有 `sys_menu` id 占用（来自全部种子脚本核对）：`1-6`(模块) `21-27`(应用) `31-36`(接口) `41-49`(权限管理+datascope) `51-55`(系统设置) `61-63`(监控) `71-74`(业务线) `81-84`(环境) `91-95`(凭证) `201-221`(页面节点)。**当前 MAX(id)=221。**

> 命名现状：种子中「业务域实体」用扁平 `<entity>:<action>`（`app:` `api:` `grant:` `env:` `biz_line:` `app_credential:` `log:call:` `alarm:handle`）；「平台/系统设置」多用 `sys:`（`sys:config:` `sys:security:` `sys:dict:` `sys:user:` `sys:role:`）。`menu.js` 的唯一离群行为：给本应扁平的 `env`/`biz_line` 加了 `sys:` 前缀，并为不存在的能力发明了新 code。

## 1. 裁决：权威侧 = 「后端 `@RequirePerm` + 现有 `sys_menu` 种子」

**结论一句话：以「后端 @RequirePerm + 现有 sys_menu 种子」为权威（扁平 snake 风格），修正前端 `menu.js`/`router` 的 2 处前缀错误，并为真正缺失的能力补种新 code。**

### 理由（四维权衡）

| 维度 | 说明 |
|---|---|
| **硬约束** | 本次任务明令「不修改任何 Java 源码」。而「统一向后端注解收敛为 `sys:` 前缀」需改 ~10 个 Controller、30+ 处注解、以及大量单测断言（如 `BizLineControllerTest`/`GrantControllerTest`/`ApiParamControllerTest` 都断言了 value 与 risk）。**该选项被硬约束直接排除。** |
| **改动面** | 采用本裁决：后端 0 改动；前端仅 **2 行**（menu.js）+ **2 行**（router/index.js）前缀修正；其余靠补种。若反向收敛：前端 0 改动但后端大面积改动 + 全量重授权。 |
| **向后兼容** | 现有种子 perm_code 已被多个角色通过 `sys_role_menu` 授权，且已登录用户的 Redis `gk:perm:{uid}` 以此为准。改 seed 值需连带改授权表 + 失效缓存。扁平风格是**既成事实契约**。 |
| **架构一致性** | 种子自身风格已自洽为主（业务域扁平 / 系统设置 `sys:`）；前端 `menu.js` 是唯一破坏者。且 `@RequirePerm` 与种子在 `env:delete`/`biz_line:delete`/`grant:revoke` 等 18 处已一致，前端不得单方面另立标准。 |
| **与 T05 计划对应** | T05 §7「路由—权限点映射」以 `menu.js` 为源；本裁决只修正其中与种子冲突的 2 项，其余保持，T05 计划无需重写。 |

### 需澄清：为何不把 `env`/`biz_line` 也统一成 `sys:`？
- 种子里 `env:list/create/update/delete`(81-84) 与 `biz_line:list/create/update/delete`(71-74) 已存在**且已被后端 `@RequirePerm("env:delete")`/`("biz_line:delete")` 引用**、已被 t03a 授权给 6 个角色。
- 若改种子为 `sys:env:*`，则必须同步改后端 2 个注解 + 重授权；收益仅是「看起来统一」，**得不偿失**，且违反硬约束方向。
- ⇒ 前端 `menu.js` 的 `sys:env:list`/`sys:bizline:list` 是**错误引用**，回退到既存扁平 code。

### 5.5 权限种子铁律（长期规则，永久生效）

> 本节是本次事故的根因固化，后续所有人新增权限**必须**遵守：

1. **一个权限点的完整定义 = `sys_menu` 一行 + `sys_role_menu` 授权若干行。**
   - `sys_menu` 行：`type=3, status=1, perm_code`（扁平 snake 码，全局唯一 `uk_menu_perm`），并按模块挂 `pid`。
   - `sys_role_menu` 行：把该 `sys_menu.id` 授予需要的角色。
   - **只插 `sys_menu`、不插 `sys_role_menu` ≡ 没播**（服务端无超管通配，任何角色都拿不到该码）。
2. **落库后必须失效缓存**：权限点集缓存在 Redis `gk:perm:{uid}`；种子写入后必须 `DEL gk:perm:*`（或 `redis-cli --scan --pattern 'gk:perm:*' | xargs redis-cli del`），否则受影响用户重新登录仍读旧缓存。
3. **id 段归属登记**：新增码须用**已预留的 id 段**，避免主键冲突。当前划分：本方案 `301–341`；T03b `96–199`（预留 100–130）；其余负责人落库前先在本台账登记段位。
4. **落库前做三差集自检**（见 §8 验证判据）：前端 `menu.js`/`router`/`PermButton` 引用码、后端 `@RequirePerm` 值，与 `sys_menu.perm_code` 的差集必须均为空。

## 8. 验证判据（执行 `seed-perm-alignment.sql` 后应达到）

1. **Class A 全绿**：`menu.js` 20 个叶 code 全部 ∈ `sys_menu.perm_code`（type=3, status=1）。
2. **Class B 差集为空**：后端 30 个 `@RequirePerm` 值全部 ∈ `sys_menu.perm_code`。
3. **Class C 差集为空**：46 处 `PermButton` 的全部 code ∈ `sys_menu.perm_code`。
4. **admin 复登（口径：先探测 → 再定期望值 → 断言）**：因 eng-t03b **并行**补 `api_param:import` / `api_version:gray` / `api_env_config:test`（实落 3 个码），admin 的 permCount 存在 **74 / 75 / 76 / 77** 四种可能，执行方**无法预知并行时序**，故不能用固定数字断言：
   - ① **探测**：`SELECT perm_code FROM sys_menu WHERE perm_code IN ('api_param:import','api_version:gray','api_env_config:test');` 得出已落库的 T03b 码数 N（0/1/2/3）。
   - ② **期望值 = 74 + N**（基线 74 = 42 + 本方案 32；`env:list`/`biz_line:list` admin 已拥有不重复计）。
   - ③ **断言** `permCount == 期望值`，且**必须逐项断言关键码存在**（不能只比总数）。
   - ⚠️ 复登前务必先 `DEL gk:perm:*`，否则读旧缓存导致计数不变（见 §5.5 铁律第 2 条）。
   - 补充盲区自查（admin 有 2 个角色，需分别覆盖）：`SELECT r.role_code, COUNT(*) FROM sys_role_menu rm JOIN sys_role r ON r.id=rm.role_id WHERE rm.menu_id BETWEEN 301 AND 341 GROUP BY r.role_code;` —— 应同时出现 `SUPER_ADMIN` 与 `ADMIN`，缺失任一即为授权漏配。
5. **页面可见性手测**：`admin` 登录 → 侧边栏应出现全部 6 模块 20 页（尤其此前不可见的 概览 / 环境与网关 / 业务线管理 / 用户管理 / 角色管理 / 操作审计 / 安全策略 / 通知渠道 / 日志与审计 / 告警记录 / 封禁管理）。
6. **403 冒烟**：以 admin 调 `DELETE /api/interface/{id}`（`api:delete`）、`PUT /api/role-data-scope/{id}`、`POST /api/block/rule` 等此前必 403 的写接口，应放行。
