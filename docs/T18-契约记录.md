## 2 核心契约

### 2.1 端点

```
POST /interface/import     权限 api:create（risk=true）  ← **零新增权限点**
请求 {groupId:Long(必填), content:String(文档正文), fileName:String?(仅提示用)}
响应 Result<InterfaceImportResult>
```

`InterfaceImportResult` = `groupId/groupName/openapiVersion/title/specVersion/serverUrl`
+ `total/imported/skipped/failed/paramCount` + `items[]`（逐条 `apiId/name/method/path/source/result/message/paramCount/warnings`）
+ `warnings[]`（全局待办提示）。

### 2.2 🔴 groupId 必填：三层闸门（本任务的核心需求）

| 层 | 位置 | 作用 |
|---|---|---|
| 1 | `InterfaceImportDialog` 的「开始导入」按钮 `:disabled="!form.groupId \|\| !content"` | 体验层：未选分组**点不动** |
| 2 | 同组件 `rules.groupId` = required（trigger change） | 二次兜底 + 红字提示 |
| 3 | `InterfaceImportServiceImpl.requireGroup()` | **真防线**，返回 400「请先选择分组：导入前必须指定接口所属分组」 |

- **为什么必须三层**：前端闸门只是体验层，`curl` 可绕；迁移/脚本场景不经过页面。
- 🔴 **校验顺序也是契约**：**先拦参数、再读文档**（否则 8MB 文档会被完整解析一遍才报"没选分组"）。单测用 `verifyNoInteractions(openApiParser)` 钉死该顺序。
- UI 级证据：空表单禁用 ⇒ **只填内容、未选分组仍禁用** ⇒ 禁用态点击**零请求零落库**（三条均实测）。

### 2.3 字段映射口径（与前端 `utils/enum.js` 对齐）

- **paramType 只有 1=Header / 3=Request / 4=Response / 5=Error（无 2=QUERY）**；OpenAPI 的 `query`/`path` 统一并入 **3(Request)**，语义靠描述前缀 `[query] ` / `[path] ` 保留（不发明枚举值，避免控制台出现无法渲染的类型）。
- **fieldType 是 `int` / `bool`**（**不是** `integer` / `boolean`），由 `mapFieldType()` 归一。
- `requestParamType` ∈ `JSON` / `FORM` / `QUERY`，由 requestBody 的 content 媒体类型推导。
- 响应分区：**2xx 且有 content/schema ⇒ Response(4)**；其余（含 default）⇒ Error(5) 且 `error_code` = 响应码。

### 2.4 幂等：`api_code` 是唯一防线

```
api_code = "imp_" + <method 小写> + "_" + <path 转义>
若 > 64 字符 ⇒ 保留前 (64-8-1) 位 + "_" + SHA-256(path) 前 8 位 hex
DB 侧 uk_iface_code 唯一键兜底
```

同一份文档重复导入 ⇒ `imported=0 / skipped=N`，明细逐条写明「已存在」。
并发下即使绕过前置存在性检查，唯一键也会把后到的判为 skipped（`DuplicateKeyException` 捕获）。

### 2.5 部分成功语义

- **整批失败**（未选分组 / 分组不存在 / content 空 / 解析失败）⇒ **400**，零落库。
- **单条失败** ⇒ 计入 `failed`，**不影响其余**。故单条落库抽成**独立 Bean `InterfaceImportWriter`**（每条 `@Transactional(rollbackFor=Exception.class)`）：若与被循环方法同处一个 Bean，自调用不走代理 ⇒ `@Transactional` **形同虚设**，一条失败会回滚整批。

### 2.6 刻意不做的事（写下来，免得下一轮被当成"漏了"再补一遍）

| 不做 | 原因 |
|---|---|
| **不创建 `api_version`** | 导入产物是**草稿**，发布走既有版本流程（`api_version` 行数实测未变） |
| **不写 `api_change_log`** | `@ApiChangeLog` 的 apiId 四级回退解析不到"一次导入 N 条"。硬挂会写出 N 条指向同一 apiId 的错误记录。导入动作由 **`OperationLogAspect`**（拦全部 controller 写操作）留 1 条操作审计 |
| **`publish_status = 0`** | 🔴 导入**不得**直接对外放行（实测断言） |
| **`backend_url` 显式空串 `""`** | 列 NOT NULL；且 spec 的 `servers[0].url` 是**网关对外地址**，写进去会**回环**（网关转发给自己）。故只在响应的 `serverUrl` 回显提示，不落库 |
| **`tags = openapi-import`** | 事后可按来源筛选导入产物 |
| `status = 1` | 网关开关默认启用（与人工新建一致） |

### 2.7 上限与截断

单份 ≤ **8MB**；≤ **500** operations；每分区 ≤ **200** 参数（超出截断 + warning）；
`$ref`/`allOf`/`oneOf`/`anyOf` 展开深度 ≤ **3** 且自引用必须收敛。
长度上限（T17 加密膨胀率反推）：path 300 / name 64 / desc 200 / 字段名 128 / 示例 512 / 参数说明 512 / 错误码 64。

## 3 实现期挖出的真实产品缺陷（3 条，都是"看着对、其实错"）

### 3.1 `swagger-models` 把 `OpenAPI.openapi` 默认初始化成 `"3.0.1"`
用 `getOpenapi()` 判「文档缺 openapi 字段」是**死代码**（永远非空）。
⇒ 改**回原文**判 `"openapi"` / `openapi:`，并**先判 Swagger 2.0 再判 3.x**（顺序即防线：2.0 正文也可能出现 openapi 字样）。已补两条回归用例钉住。

### 3.2 🔴 `Schema.getRequired()` 的两个反直觉行为（`allOf` 合并时 NPE）
1. `setRequired(空列表)` 后 `getRequired()` 返回 **null**（不是空列表）；
2. `getRequired()` 返回的是**拷贝**（`sameInstance == false`）⇒ 往 getter 返回值上 `addAll` **静默无效**。
⇒ 改为**局部累积 `mergedProps`/`mergedRequired`，末尾一次性 set**，空 required 不 set。结论由 Java 探针实测确认（不是推测）。

### 3.3 Controller 端点"报成功但没落盘"⇒ 4 条用例全 500
`grep importSpec` 无命中、请求报 `HttpRequestMethodNotSupportedException`。
**不是代码写错，是编辑器写入未持久化**（本项目已多次遇到）。⇒ 读回校验后重做，端点上线。
**教训：任何写入都必须读回校验，"Successfully edited" 不算证据。**

## 4 本轮暴露的机制性问题（都已固化，值得下一轮直接复用）

### 4.1 🔴 客户端错误被伪装成服务端故障（已修，且这是通用缺陷）
`{"groupId": [12]}`（数组塞进 Long 字段）触发 Jackson `MismatchedInputException`，而 `GlobalExceptionHandler` **没有** `HttpMessageNotReadableException` 分支 ⇒ 落到兜底 `Exception` ⇒ 客户端收到 **500「系统繁忙，请稍后重试」**，把"我传错了"误判成"服务挂了"并制造无意义告警。
⇒ 新增 `handleMessageNotReadable` → **400**，对外只给通用提示（**不回显内部 DTO 类名/包名/引用链**，只写日志），并补 5 条单测钉死 400/500 的归属边界。

### 4.2 探针的 `one()` 返回的是**行元组**，不是标量
`db()` 返回行元组列表，`one()` 写 `r[0]` 得 `(12,)`，序列化成 JSON **数组** ⇒ 撞上 §4.1 的 500，伪装成"导入功能整个坏了"（A4 起全 500）。实为**探针自身缺陷**。⇒ 改 `r[0][0]`。
**通则：断言失败先怀疑探针；`all([]) == True` 与"空列表下 `all(...)` 假绿"同族。**

### 4.3 探针工具函数缺失会把整段断言打成 error
`cdp_t18_ui.js` 的 `HELPERS` 漏了 `rowsOf`/`cellsOf` ⇒ 结果态 `Runtime.evaluate` 抛 `window.__T.rowsOf is not a function` ⇒ 14 条断言连锁假失败（含 `__STATS__` 变 null），**而界面其实完全正常**。

### 4.4 两个 UI 探针专属陷阱（首次踩到，已固化）
1. 🔴 **`querySelector('.el-cascader__dropdown')` 会命中"另一个"隐形下拉**：接口列表工具栏的分组筛选也是 el-cascader，未展开的那个仍留在 DOM（`display:none`）⇒ 取第一个永远拿到隐藏的 ⇒ 表现为「下拉没展开」（**探针缺陷**，与 skill §3.8 同族）。⇒ 取**全部 dropdown 按高度过滤可见的、取最后一个**（沿用 `cdp_subtree_ui.js` 写法）。
2. 🔴 **别把字符串塞进取文本的工具函数**：`txt(x.value)` 内部取 `textContent`，字符串没有 ⇒ 返回空串 ⇒ 判据恒不成立。首跑分组**其实已选中**（`back.sel` 已回显分组名），却报"选择失败"。
3. **就绪锚点必须与权限无关**：首跑用「新建接口」当锚点，但普通用户本来就**不该有**该按钮 ⇒ "无权限"被误判成"页面没渲染"，E 段 4 条假失败。⇒ 改用工具栏筛选框的 placeholder。

## 6 遗留项（含已闭环）

### 6.1 ✅ 已闭环（2026-09-17）：`OperationLogAspect` 的"排除 /auth 与 /gateway"分支**恒不生效**

**原缺陷（T18 收尾时发现，当时只记录未改）**
```java
// OperationLogAspect#around
if (!isWriteMethod(method) || uri.startsWith("/gateway") || uri.startsWith("/auth")) { ... }
```
`request.getRequestURI()` **包含 context-path `/api`**（同文件 `record()` 的注释自己写明
`segments = ["", "api", "app", ...]`）⇒ `uri.startsWith("/gateway")` / `("/auth")` **永远为假**。
**当时实测**：`sys_operation_log` 中 `/api/auth/login` **142** 行、`/api/gateway/*` **23** 行。

**根因**：同一份"按路径首段判断"的逻辑，`record()` 的模块推导**已经**剥了 context-path
（T10-E 修正过，取 `segments[2]`），而排除判断**没剥** ⇒ **两端口径分叉**。

**修复（`f407a9c` 之后新一轮）**
- 抽出唯一口径 `businessPath(request)`：用 `getRequestURI().substring(getContextPath().length())`
  （**不硬编码 `/api`**，换 context-path 也不失效），排除判断与模块推导**共用**它；
- 排除判定由 `startsWith("/gateway")` 改为**首段等值** `EXCLUDED_SEGMENTS.contains(firstSegment(path))`
  —— 前缀匹配会把将来的 `/authorization`、`/gateway-report` 一并静默排除（隐性误伤）；
- `requestUrl` **仍存完整含 `/api` 的路径**，既有数据形状不变。

**同族旁证**：`config/WebConfig` 的 javadoc 早已写明同类坑——
> 应用配置 context-path=/api，Spring MVC 的拦截器路径匹配基于去掉 context-path 之后的路径，
> 因此这里不能再写 /api 前缀，否则规则永远匹配不上，管理接口将处于零鉴权状态。

即同类坑项目已踩过一次，`WebConfig` 记住了，`OperationLogAspect` 没记住。

### 6.3 ✅ 已闭环（2026-09-17）：审计模块下拉与后端枚举**漂移** —— 但修法不是"补两项"

**原发现**（本轮首版记录）：后端 `OperationLogAspect.MODULE_MAP` 有 **7** 项，前端
`views/system/SysLog.vue` 与 `views/perm/PermAudit.vue`（**常量在两处重复**）各只有 **5** 项，
缺 `GROUP` / `ENCRYPTION` ⇒ 分组、加解密配置的操作**能被列表看到、却无法在下拉里筛出来**。
当时的建议是"把这两项补进列表，并把常量抽到 `utils/enum.js` 单一来源"。

**动工前先查库 —— 结论推翻了原建议**（这正是"先探测、再动手"的价值）：

| 事实 | 实测 |
|---|---|
| 库中 `operation_module` 真实出现过的值 | **18 个**（`INTERFACE` 148 / `AUTH` 144 / `APP-CREDENTIAL` 36 / … / `ENV` 1） |
| 前端硬编码那 5 项能覆盖其中几个 | **4 个** |
| 前端硬编码的 `LOGIN` / `LOGOUT` | 切面只产 `CREATE/UPDATE/DELETE` 且登录已排除 ⇒ **永远不会被写入**（死项） |
| 前端硬编码的 `SECURITY` | 库中 **零行**（死项） |
| `operation_type` 真实值域 | 只有 `CREATE` 446 / `DELETE` 59 / `UPDATE` 50 |

⇒ **`MODULE_MAP` 不是"值域"，它只是"首段 → 模块名"的改名表**；
`operation_module` 的真实值域**随 controller 首段增减而变**（未命中映射的走"首段大写"兜底）。
所以"往列表里补几个模块名"**永远是错修法**：今天补齐 18 个，明天新增一个 controller 就又不全。
**最终修法（本轮落地）：值域改由后端按库里 `DISTINCT` 下发**
- 新增 `GET /system/operation-log/filter-options` → `{modules:[...], types:[...]}`
  （`SELECT DISTINCT`；**零新增权限点**，与 `/operation-log/list` 同裁定；
  对齐 T11 `GET /alarm-rule/target-options` 先例）。
  回源链路：`SysOperationLogMapper.selectDistinctModules/Types` → `OperationLogOptionsVo`
  → `SysOperationLogServiceImpl.filterOptions()`；`types` 按 `CREATE/UPDATE/DELETE` 优先、其余排序追加。
- 前端 `utils/enum.js` 只保留**本地兜底**常量（后端拉不到时**静默回退、不弹错**——
  用户没做错任何事），`SysLog.vue` / `PermAudit.vue` 两处改为**同一来源**。
- 效果实测（UI 探针）：模块下拉 **18 项 == 接口值域**（逐元素相等，不是"包含"）；
  选中 `GROUP` → 页面「共 30 条」== 库里 `GROUP` 30 行；重置后选中 `CREATE` → 「共 446 条」== 446。

### 6.4 🆕 验证途中挖出的**既有** 500（2026-09-17，顺带修复）：`/dashboard/screen/{app-rank,interface-rank}`

**现象**：跑 T18 UI 探针时 7.1「无 HTTP ≥ 400 响应」失败，报
`500 /api/dashboard/screen/interface-rank`、`500 /api/dashboard/screen/app-rank`。

**定位（三步，缺一不可）**：
1. **脱离 UI 复现**——同一 token 直连这两个端点仍 500（`/screen/overview` 是 200）⇒ 与页面、探针无关；
2. `git status` 确认 `DashboardController.java` **不在**本轮改动清单 ⇒ **既有缺陷**；
3. 日志 NPE 落点 `DashboardServiceImpl.appRank:146` / `interfaceRank:184`；`javap -c -l` **确认首条指令就是 `aload <循环变量>`** ⇒ **对 null 解引用**（同一 SQL 在 DB 侧实测正常）。

**根因**：MyBatis 的 `returnInstanceForEmptyRow` **默认为 false**——当某行**所选列全部为 NULL** 时，`selectList` 放进 List 里的**不是空实体，而是 `null` 元素**。这两个排行方法恰好 `select("app_id","app_name")` / `select("interface_id","interface_path")`，**只选部分列、且不选主键**；库里确实存在"网关未解析出应用/接口"的调用日志（实测今日 id=39、40 四列全 NULL）⇒ for-each 解引用即 NPE ⇒ 端点恒 500。

**修法**：两处循环加 `if (log == null) continue;`（带注释说明该 MyBatis 形态），**不动全局配置**——改成 `return-instance-for-empty-row: true` 会波及所有查询，违背"不做全局行为变更"。新增 `DashboardServiceImplRankNullRowTest` **7 例**，每个用例都往列表里塞 `null` 元素 ⇒ **去掉守卫立刻 NPE 失败**（可证伪，不是平凡通过）。

**连带结论（值得固化）**：全仓 5 处 `.select(...)` 里，只有这 2 处不选主键 ⇒ 只有它们中招；`ApiParamServiceImpl:626`、`RoleDataScopeServiceImpl:58/93` 都选了 `id`，天然免疫。**以后写"部分列投影"务必带上主键列，或显式容忍 `null` 元素。**



## 7 环境坑（本轮新增，★ 高频）

1. 🔴 **方向：先怀疑探针，再怀疑产品**。本轮 5 次 FAIL 全是探针缺陷（§4.2/§4.3/§4.4），产品一处没错。`all(...)` 在空列表上恒真 ⇒ 断言必须带 `b_ok`/`p_ok` 前置。
2. 🔴 **bash 下 `npm run build` 会报 `/usr/bin/env: 'bash': No such file`** ⇒ 必须换 PowerShell 工具跑。
3. **沙箱重定向读文件过早会读到 0 字节**（python 输出有缓冲）⇒ 用 `-u`，或等后台任务结束再读；文件大小 0 不代表失败。
4. 🔴 **校验脚本的基线不能写死常数**（本轮连踩两次，同根因：把"某一轮的预期"当成"永久不变的真值"）：`t18_perm_redline.py` 曾把「96 条 / 65 码」硬编码成 T17 基线（那是 2026-09-12 的数字，早被 T13~T17 撑大）、又写死「注解条数必须恰好 +1」⇒ HEAD 一变就报"与预期不符"，**是脚本陈旧被误读成"代码越界"**。⇒ 改为从 `git HEAD` 现算基线（`git grep` + 同一套按行正则）；**不同码 +0 是硬约束**，注解条数差值仅作参考输出，需强校验时用 `--expect-occ-delta=N` 显式声明。
5. **A/B 两相探针法（本轮固化，值得复用）**：同一支探针接受 `legacy|fixed` 参数切换**期望值**，先对**改动前的进程**跑一遍——**必须先看到 FAIL**；若 legacy 相就全绿，说明探针根本测不到该差异（恒绿空断言），此时"fixed 相全绿"毫无意义。判据：*两相结论相反，才证明差异由改动造成*。本次直接复用运维留在 8080 上**尚未重启的旧进程**当 legacy 相，零额外重启成本。
6. 🔴 **探针自身的"步骤遗漏"会伪装成产品缺陷（2026-09-17 踩到）**：UI 探针先选「操作模块 = GROUP」筛选，**未重置**就接着选「操作类型 = CREATE」，两个条件在查询里是**交集** ⇒ 页面「共 22 条」对不上库里 `CREATE` 全量 446，报出来却像"筛选算错了"。**修法：连续筛选之间必须先点「重置」**，并在断言里加自检（`6.0b 重置后模块输入框已清空`）+ 反证（`6.3 结果 ≠ 未重置时的交集值 22`）。**这条已第二次体现"先怀疑探针"（§4.x 同族）。**
