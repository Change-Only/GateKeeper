## 6. 缺陷与修复（本次验证发现并修复）

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 应用**启动失败**：`IllegalArgumentException: error at ::0 formal unbound in pointcut`（`ProxyTransactionManagementConfiguration` 初始化失败） | `ApiChangeLogAspect` 用 `@annotation(全限定名)` 匹配，却同时声明了注解类型形参 `ApiChangeLog annotation`——该形参未被任何切点绑定，AspectJ 启动期报「formal unbound」 | 改为在通知内**反射**从方法签名读取注解（`resolveAnnotation`），通知签名收敛为 `(JoinPoint, Object result)` |
| 2 | `PUT /gray`、`POST /test` **不写留痕**（6 个写操作只落了 3 条） | Controller 统一返回 `Result<T>` 包装体，真正的 DTO 在 `data` 里；`resolveApiId` 只对裸返回对象解析 `getApiId()`，对包装体解析不到 apiId → 跳过留痕。`upsert`/`create`/`batch-save` 因 apiId 能从**入参**拿到而幸免 | 新增 `unwrap(Object)`：`Result` 则取 `data` 再解析 apiId，且 `newValue` 落**业务对象 JSON**（而非包装体）；补单测锁定 |
| 3 | 种子后首次调用新接口返回 **403 无权限操作：api_param:import** | `admin` 的 `gk:perm:1`（Redis SET，TTL 24h）是**种子之前**登录写入的旧快照；登录走缓存命中，不回源 DB | 运维动作：`DEL gk:perm:1` 后重新登录即回源 DB（生产环境权限变更应走 `PermissionCacheService.invalidateUser`）。已附于报告供部署参考 |
| 4 | 环境连通性测试恒为「已配置(1)」，未变「已验证(2)」 | 探测目标选用了 `HEAD /api/auth/login`，该路径对 HEAD 返回 **500**（非 `<500`）；且 `localhost` 在 JVM 内可能解析到 IPv6 `::1` | 探测目标改用 `http://127.0.0.1:8080/api/interface/list`（HEAD→401，`<500` 即视为连通），显式 IPv4 |

> 修复 #1、#2 后重跑全量单测 346/0、重启应用成功、e2e 11 步全绿。
